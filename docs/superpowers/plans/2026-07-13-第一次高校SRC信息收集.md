# 第一次高校 SRC 漏洞挖掘 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 完成对一所目标高校的完整三层信息收集与初步测试，产出一份资产清单和至少 3 个值得深入测试的系统列表。

**Architecture:** 3 个阶段共约 4-6 小时（可分 2-3 天完成）。阶段 A 零风险被动收集，阶段 B 轻量主动探测，阶段 C 资产分析与初步手工测试。每个阶段产出明确交付物，不跳跃。

**Tech Stack:** Windows 终端 (Git Bash/PowerShell), Burp Suite Community, subfinder, dnsx, httpx, 浏览器

## 全局约束

- 所有主动请求限制在每秒 5-10 个
- 不扫描目录、不跑漏洞 POC、不批量发包
- 不碰内网 IP（即使被动收集到）
- 发现漏洞即停止深入，不拖数据
- 只测对外网开放的系统

---

## 阶段 A：第一次被动侦察（约 1.5 小时，零风险）

### 任务 A1：选定第一个目标学校

**产出:** 一个确定的目标域名

- [ ] **Step 1: 选一个学校**

不要一上来就选清华北大这种头部 985——它们安全投入大，新手很难出洞。从中等规模的省属高校入手，它们系统多、安全投入有限、资产暴露面大。

**策略**：从你的省份选一所普通本科院校，或者你熟悉的学校。记下它的官方域名，比如 `xxx.edu.cn`。

```
目标域名: __https://www.cdcas.edu.cn___
学校全称: _____成都文理学院_____
```

- [x] **Step 2: 确认域名格式**

在浏览器直接打开 `https://www.xxx.edu.cn`，确认它是该学校的官方主站。如果打不开或跳转到其他域名，记录下来。

---

### 任务 A2：crt.sh 证书透明度查询

**产出:** 第一批子域名列表

- [x] **Step 1: 打开 crt.sh**

浏览器访问：
```
https://crt.sh/?q=%25.xxx.edu.cn
```
（把 `xxx.edu.cn` 替换成你的目标）

- [x] **Step 2: 导出子域名列表**

页面上会列出该域名下所有 SSL 证书记录。重点关注 `Common Name` 和 `Matching Identities` 列。

手动复制所有出现的域名到记事本，一行一个。预期一个普通高校会有 20-100 条。

- [x] **Step 3: 去重和清洗**

```bash
# 在 Git Bash 中执行
sort crt_raw.txt | uniq > crt_dedup.txt
```

- [ ] **Step 4: 标记可疑资产**

扫一眼列表，把以下类型的域名标注出来：
- 包含 `admin`, `manager`, `oa`, `jw`, `jwc`, `教务` 的 → 后台/业务系统
- 包含 `vpn`, `sso`, `cas`, `idp` 的 → 基础设施
- 包含 `test`, `dev`, `demo` 的 → 测试环境，大概率防护弱
- 看起来不像学校官方的域名 → 可能是废弃项目，也可能是敏感资产

不需要深入分析，先标注。

---

### 任务 A3：搜索引擎语法收集

**产出:** 补充的子域名和 URL 路径

- [ ] **Step 1: Bing 搜索**

在 Bing (bing.com) 中依次搜索以下语法，把搜索结果前 3 页出现的**新域名和新路径**记录下来：

```
site:xxx.edu.cn inurl:login
site:xxx.edu.cn inurl:admin
site:xxx.edu.cn filetype:php
site:xxx.edu.cn filetype:jsp
site:xxx.edu.cn filetype:asp
site:xxx.edu.cn intitle:"管理"
site:xxx.edu.cn inurl:upload
site:xxx.edu.cn inurl:id=
```

- [ ] **Step 2: Google 搜索（如果能访问）**

同样的语法在 Google 跑一遍，Google 的收录通常比 Bing 更广。

- [ ] **Step 3: 合并结果**

把搜索引擎发现的域名合并到 crt.sh 的列表里，去重。

---

### 任务 A4：FOFA 查询

**产出:** 端口和服务信息

> 如果没有 FOFA 账号，注册一个免费版即可（fofa.info）。免费版有查询次数限制，但够用。

- [ ] **Step 1: FOFA 域名查询**

```
domain="xxx.edu.cn"
```

- [ ] **Step 2: FOFA 证书查询**

```
cert="xxx.edu.cn"
```

- [ ] **Step 3: 记录发现**

重点关注 FOFA 返回的：
- 开放端口（除了 80/443 之外的端口尤其值得关注）
- 服务 banner（Apache/Tomcat/Nginx/IIS 版本号）
- 页面标题

把这些信息追加到你的资产清单中。

---

### 任务 A5：GitHub 泄露搜索

**产出:** 可能的敏感信息泄露线索

- [ ] **Step 1: GitHub 搜索**

在 GitHub 搜索框中依次输入（每次一个）：

```
"xxx.edu.cn" password
"xxx.edu.cn" jdbc
"xxx.edu.cn" secret
"xxx.edu.cn" api
```

- [ ] **Step 2: Gitee 搜索（国内高校代码多在 Gitee）**

同样的关键词在 Gitee (gitee.com) 搜索一遍。

- [ ] **Step 3: 记录发现**

如果发现任何泄露的配置信息、内网地址、数据库连接串，记录到单独的文件，**仅记录不利用**。这些在第三层可能会用到。

---

### 阶段 A 交付物检查

在进入阶段 B 之前，确认你手上有了：

- [ ] 一个去重后的子域名列表（至少 20+ 条）
- [ ] 每个域名标注了来源（crt.sh / Bing / FOFA）
- [ ] 可疑/有趣的域名已被标注
- [ ] FOFA 发现的非标端口和服务已记录
- [ ] GitHub/Gitee 泄露线索已记录（如有）

## 阶段 B：轻量主动探测（约 1 小时）

> **注意**：从这里开始会向目标发送网络请求。严格遵守限速和请求范围约束。

### 任务 B1：环境确认

**产出:** 工具可用性确认

- [ ] **Step 1: 检查 subfinder**

```bash
subfinder -version
```

如果提示命令不存在：
```bash
# Windows 下用 scoop 或直接下载 exe 放到 PATH 里
# 或者用 OneForAll (Python) 替代
```

- [ ] **Step 2: 检查 dnsx**

```bash
dnsx -version
```

- [ ] **Step 3: 检查 httpx**

```bash
httpx -version
```

三个工具都确认可用后继续。

---

### 任务 B2：子域名收集与 DNS 验证

**产出:** 确认解析的子域名列表

- [ ] **Step 1: 准备输入文件**

把阶段 A 收集到的所有域名（去重后）放入一个文件 `target_domains.txt`，每行一个域名。

- [ ] **Step 2: 运行 subfinder**

```bash
subfinder -dL target_domains.txt -o subs_new.txt
```

`-dL` 表示从文件读取域名列表。

- [ ] **Step 3: 合并并去重**

```bash
cat target_domains.txt subs_new.txt | sort -u > all_subs.txt
```

- [ ] **Step 4: DNS 解析验证**

```bash
dnsx -l all_subs.txt -resp-only -o resolved.txt
```

`-resp-only` 只输出成功解析的域名。

看一眼 `resolved.txt` 有多少条。一个正常高校应该有 30-100+ 个可解析的子域名。

---

### 任务 B3：存活检测与指纹识别

**产出:** 存活资产清单（带指纹）

- [ ] **Step 1: 运行 httpx**

```bash
httpx -l resolved.txt -title -status-code -tech-detect -o alive.txt
```

这会需要几分钟。观察终端输出，确保请求速度在合理范围。

- [ ] **Step 2: 浏览结果**

打开 `alive.txt`，每一行格式类似：
```
https://portal.xxx.edu.cn [统一身份认证] [200] [Java, Spring, jQuery]
```

- [ ] **Step 3: 分类标记**

按指纹分类，重点关注：

| 指纹关键词 | 标记为 |
|-----------|--------|
| Tomcat, WebLogic, Struts2, Shiro | **最高优先级 — 已知漏洞框架** |
| PHP, ASP.NET, Django, Flask | **高优先级 — 自研系统** |
| Nginx, Apache, IIS (only) | **中优先级 — 需要进一步分析** |
| 空或只有 CDN | **低优先级 — 可能是静态站点或全站加速** |

---

### 阶段 B 交付物检查

在进入阶段 C 之前，确认：

- [ ] 有了一份存活资产清单 `alive.txt`（30-100+ 条）
- [ ] 资产已按指纹分类标记优先级
- [ ] 没有运行任何目录扫描或漏洞扫描
- [ ] 请求速度没有失控（没有触发 WAF 或被封 IP）

## 阶段 C：资产分析与初步测试（约 2-3 小时）

### 任务 C1：筛选 3-5 个目标系统

**产出:** 优先测试列表

- [ ] **Step 1: 拎出"最高优先级"资产**

从 `alive.txt` 中捞出所有标记了已知漏洞框架（Tomcat/WebLogic/Struts2/Shiro）的域名。

- [ ] **Step 2: 拎出"高优先级"资产**

独立登录页、非 SSO 认证的系统、自研系统。

- [ ] **Step 3: 手动浏览**

在浏览器中逐个打开这些系统，**不挂 Burp**，只是正常浏览，了解：
- 这是什么系统？（教务、OA、图书馆、一卡通、VPN...）
- 有没有登录页？登录页长什么样？
- 有没有对外开放的功能（查询、搜索、留言）？
- 页面是否看起来老旧？（老旧的 UI 通常意味着老旧的代码）

- [ ] **Step 4: 选定第一批测试目标**

从浏览过的系统中选出 **3-5 个**值得深入测试的，记录选择理由。

---

### 任务 C2：对第一个目标系统进行手工测试

**产出:** 测试记录（可能包含漏洞发现）

- [ ] **Step 1: 挂上 Burp，正常使用**

打开 Burp Suite，配置浏览器代理。访问目标系统，正常浏览所有你能看到的功能。不要输入任何 payload。

- [ ] **Step 2: 检查"意外暴露"**

在 Burp 的 HTTP History 和响应内容中查找：

```
# 响应头
Server: Apache/2.2.15    → 老版本
X-Powered-By: PHP/5.3    → 老版本
Set-Cookie: JSESSIONID   → Java 应用

# 响应体（在 Burp 中搜索）
<!--                    → HTML 注释，可能泄露路径
password                → 硬编码密码
jdbc:mysql              → 数据库连接串
192.168.                → 内网 IP
10.                     → 内网 IP
```

- [ ] **Step 3: 测试未授权访问**

在浏览器地址栏尝试访问常见的后台路径：
```
/admin
/manager
/console
/swagger-ui.html
/actuator
/druid
/.git/config
```

每尝试一个路径，观察返回：200/302 表示可能存在未授权访问；404/403 表示不存在或已防护。

- [ ] **Step 4: 测试登录页**

如果目标系统有登录页：
- 尝试 `admin` / `admin`
- 尝试 `test` / `test`
- 查看登录请求的参数（用户名和密码的参数名是什么）
- 查看是否有"忘记密码"功能

- [ ] **Step 5: 测试输入点**

如果系统有查询/搜索/表单功能：
- 在输入框输入一个单引号 `'`，看返回是否报错或变化
- 输入 `<script>alert(1)</script>`，看是否被过滤还是原样输出

**记住**：这一轮的目标是找到"有反应的参数"，不是立刻挖出漏洞。有反应就记下来，没反应就换下一个。

- [ ] **Step 6: 记录测试结果**

无论是否发现漏洞，记录下来：

```
目标系统: jwxt.xxx.edu.cn
测试时间: 2026-07-13
测了哪些点:
  - /admin → 302 跳转到登录页（正常）
  - /swagger-ui.html → 404（不存在）
  - 登录页 admin/admin → 失败
  - 搜索框输入 ' → 返回空白页（可疑！可能注入点）
结论: 搜索框参数 keyword 需要继续测试
```

**产出:** 下次测试的明确方向

- [ ] **Step 1: 整理本次成果**

## 备忘：常见踩坑

1. **httpx 请求太快被封 IP** → 加 `-rl 5` 参数限速
2. **subfinder 返回空** → 检查网络是否能访问公共 DNS，用 `-all` 参数启用所有数据源
3. **Burp 挂上后网站打不开** → 检查 Burp 的 Intercept 是否开着（应该关掉 Intercept，只在 HTTP History 中观察）
4. **所有系统都是 403** → 正常现象，高校很多系统只对内网开放，记录后跳过即可
5. **看到一个系统不确定能不能测** → 回头看合规底线六条，有任何一条可能违反就跳过
