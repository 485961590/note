# 国内高校 SRC 信息收集与测试方法论

> 适用对象：国内高校/大学 `.edu.cn` 域名的漏洞挖掘
> 前提：已掌握基础 Web 漏洞原理（SQL 注入、XSS、CSRF、XXE、SSTI 等）

---

## 一、整体框架：三层递进模型

```
第一层：被动侦察 (Passive Recon)  ──  零风险，不碰目标
第二层：轻量主动探测 (Light Active Probing)  ──  仅 DNS + 首页请求
第三层：定向测试 (Targeted Testing)  ──  手工验证，一人一次一个点
```

核心原则：**每层产出足够信息后再进入下一层。** 第一二层做扎实了，第三层才有用武之地。

---

## 二、第一层：被动侦察 (Passive Recon)

**目标**：不向目标发送任何请求，仅通过第三方公开数据源收集资产。
**合规性**：完全合法。所有数据来自第三方平台，不访问目标系统。

### 2.1 证书透明度日志

```
# crt.sh
https://crt.sh/?q=%25.edu.cn
```

拿到历史上所有 SSL 证书中出现的子域名，包括已下线和内网域名。这是最重要的被动信息源。

### 2.2 网络空间搜索引擎

使用 FOFA、Shodan、ZoomEye 查询：

```
domain="xxx.edu.cn"
cert="xxx.edu.cn"
title="xxx大学"
```

这些平台已经采集了公网暴露的服务、端口、banner，查询行为不构成主动扫描。

### 2.3 搜索引擎语法

```
site:xxx.edu.cn inurl:login
site:xxx.edu.cn filetype:php
site:xxx.edu.cn intitle:"后台管理"
site:xxx.edu.cn inurl:upload
site:xxx.edu.cn inurl:id=
```

Bing 在国内可直接使用，对中文内容收录好。搜索引擎爬虫替你爬过的内容，零风险。

### 2.4 备案信息查询

通过 ICP 备案查询 (`beian.miit.gov.cn`) 查目标学校备案号，获取同一备案主体下的所有域名。很多非 `.edu.cn` 的资产藏在备案里。

### 2.5 代码仓库泄露监控

在 GitHub / Gitee 搜索：

```
"xxx.edu.cn" password
"xxx.edu.cn" jdbc
"xxx.edu.cn" api_key
"xxx.edu.cn" secret
```

### 第一层产出物

去重后的域名和 IP 清单：

| 子域名 | 来源 | 备注 |
|--------|------|------|
| portal.xxx.edu.cn | crt.sh | 统一身份认证 |
| jwxt.xxx.edu.cn | FOFA | 教务系统 |
| 10.x.x.x | GitHub 泄露 | 内网 IP，仅记录不测试 |

## 三、第二层：轻量主动探测 (Light Active Probing)

**目标**：DNS 解析 + HTTP 首页请求，确认资产存活并获取指纹。
**合规性**：相当于用浏览器打开网页，每次只请求首页，不探测漏洞。

### 3.1 子域名收集与验证

```bash
# 子域名收集（仅公开 DNS）
subfinder -d xxx.edu.cn -o subs.txt

# 验证 DNS 解析
dnsx -l subs.txt -resp-only -o resolved.txt
```

### 3.2 存活检测与指纹识别

```bash
# 首页请求 + 指纹
httpx -l resolved.txt -title -status-code -tech-detect -o alive.txt
```

每条记录：响应状态码、页面标题、技术栈（jQuery 版本、中间件、CMS）。

### 3.3 第二层红线

**禁止做以下操作：**
- 目录扫描（dirsearch / gobuster / ffuf）
- 漏洞 POC 扫描（nuclei / xray / afrog）
- 发送任何带 payload 的请求（包括 SQL 注入、XSS 测试字符串）
- 高并发请求（限制在每秒 5-10 个请求）

**原因**：目录扫描会产生大量 404 请求，日志特征明显，本质上已是漏洞探测行为。放在第三层，针对特定子域名手工跑。

### 第二层产出物

| 域名 | 标题 | 状态码 | 技术栈 |
|------|------|--------|--------|
| portal.xxx.edu.cn | 统一身份认证 | 200 | Java, Spring |
| jwxt.xxx.edu.cn | 教务管理系统 | 200 | Tomcat 7.0, jQuery 1.x |
| vpn.xxx.edu.cn | SSL VPN | 403 | - |

## 四、第三层：定向测试 (Targeted Testing)

**目标**：针对有价值入口手工验证漏洞，不使用自动化扫描器。
**核心**：找"可疑入口"而非扫漏洞。每个入口手工构造 payload。

### 4.1 资产优先级排序

| 优先级 | 资产特征 | 原因 |
|--------|----------|------|
| 最高 | 老旧中间件 (Tomcat 6-7, IIS 6, WebLogic, Struts2) | 已知高危漏洞多，公开 POC 可参考 |
| 高 | 非 SSO 的独立登录页、自研系统 | 大概率未经安全测试 |
| 中 | 文件上传入口、搜索框、留言板、查询页面 | 有输入就有攻击面 |
| 低 | 纯静态页面、统一身份认证门户 | SSO 通常经过加固 |

一个学校的资产中，第一轮真正值得测的通常只有 **3-8 个系统**。

### 4.2 高校系统常见漏洞类型（按难度排序）

**（1）信息泄露 / 未授权访问（最常见）**

- `.git/config`、`.svn/entries` 泄露源码
- `/swagger-ui.html`、`/actuator`、`/druid` 暴露 API/监控
- 未授权直接访问的后台页面（SSO 配置遗漏）
- 响应包中携带内网 IP、数据库连接串、调试信息

**（2）弱口令 / 默认口令**

- admin/admin、test/test、guest/guest
- 学号=密码
- 老旧设备/VPN 厂商默认口令未修改

**（3）已知框架/中间件漏洞**

根据第二层指纹对照：

| 指纹 | 可能的漏洞方向 |
|------|---------------|
| Struts2 | S2-xxx 系列 RCE |
| Tomcat 6-7 | CVE-2017-12615 (PUT 上传), weak manager console |
| WebLogic | 反序列化 RCE |
| Shiro | rememberMe 反序列化 |
| PHP 站点 | 反序列化、文件包含 |
| IIS 6 | PUT 上传、短文件名泄露 |

**（4）通用 Web 漏洞（你 PortSwigger 练过的）**

- 搜索框 / 查询参数 → SQL 注入
- 用户输入回显 → XSS（反射/存储/DOM）
- 文件上传功能 → 文件上传漏洞
- CORS 头配置 → 跨域配置不当
- 密码修改 / 个人信息修改 → CSRF

### 4.3 单个目标的测试流程

```
选定目标系统的一个功能点
    ↓
正常使用，Burp 挂上，抓包观察请求/响应 → 理解业务逻辑
    ↓
在单个参数上手工构造一个最小 payload → 观察应用反应
    ↓
有异常反应 → 深入验证漏洞存在性（不利用、不拖数据）
无异常 → 换下一个参数或下一个系统
```

**关键习惯**：一次只测一个参数的一个 payload，不批量跑字典。

### 4.4 合规底线（必须遵守）

1. **限定范围**：只测学校对外网开放的系统，不碰内网（即使被动收集到了内网 IP）
2. **不破坏数据**：SQL 注入不做 update/delete/drop，只用 select/union 验证
3. **不拖数据**：验证漏洞存在即可，不导出任何实际数据
4. **不越权**：用自己的账号测试，不访问他人信息
5. **发现漏洞即停**：确认存在后停止深入利用，不顺着漏洞摸到其他系统
6. **报告走正规渠道**：教育行业 SRC 平台（补天教育板块、漏洞盒子教育板块），或学校网络中心/信息办邮箱

### 4.5 实践示例

假设第二层发现 `jwxt.xxx.edu.cn`（教务系统，指纹 Tomcat 7 + jQuery 1.x）：

```
1. 浏览器打开，Burp 挂上，正常浏览首页和登录页
2. 尝试直接访问 /admin、/manager → 看是否有未授权访问
3. 检查响应头和 HTML 源码 → 看有没有注释泄露路径/账号
4. 登录页用户名输入 admin' → 观察是否有 SQL 报错
5. 尝试 admin/admin、test/test 弱口令
6. 如果有"忘记密码"功能 → 测试用户名枚举
7. 如果进了系统，找查询功能 → 测试参数注入
```

一个学校认真测完需要 **3-5 天**，不是一个下午能搞定的事。

## 五、心态与节奏

### 5.1 现实的预期

- 挖不到是正常的，十个学校出一个洞就算不错
- 新手第一个有效漏洞往往在第 20+ 次尝试后才出现
- 信息收集决定上限，80% 的时间花在前两层，20% 花在测试

### 5.2 推荐的学习-实战循环

```
学一个漏洞类型 → 在 PortSwigger Lab 练到熟练 → 去真实高校找这种漏洞
```

比如：这周学 XXE → PortSwigger XXE 全部打通 → 去高校找 XML 上传/解析入口 → 不管找没找到，下周换下一个类型。

### 5.3 记录与复盘

每次测试后记录：
- 目标学校、测试时间
- 发现了哪些资产、哪些值得深入
- 测了什么点、用了什么 payload
- 为什么没出洞 / 为什么出洞了
- 下一步该提升什么

这些记录本身就是你的方法论积累，比单个漏洞值钱。
