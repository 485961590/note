# OWASP Top 10 (2021)

## 概述

**OWASP** (Open Web Application Security Project) 是一个开源的、非盈利的全球性安全组织，致力于提高软件安全性。其核心产出之一是 **OWASP Top 10**——一份面向开发者和安全从业者的 Web 应用程序最严重安全风险列表。该列表基于社区贡献的数据，经方法论统计排名得出，每 3-4 年更新一次，当前最新版本为 **2021 年版**。

OWASP Top 10 的定位并非"最常出现的漏洞"排行，而是**风险**排行——综合考虑了漏洞的普遍性、可检测性、可利用性和业务影响。它被广泛引用为 Web 安全基线标准，也是 PCI DSS、ISO 27001 等合规体系的参考依据。

---

## OWASP Top 10 (2021) 完整列表

| 编号 | 类别 | 核心问题 |
|------|------|---------|
| **A01** | 失效的访问控制 (Broken Access Control) | 用户可以做超出其权限范围的操作 |
| **A02** | 加密机制失效 (Cryptographic Failures) | 敏感数据未被正确加密保护 |
| **A03** | 注入 (Injection) | 用户输入被当作代码/指令执行 |
| **A04** | 不安全的设计 (Insecure Design) | 架构和设计阶段的安全缺陷 |
| **A05** | 安全配置错误 (Security Misconfiguration) | 默认配置、不完整配置、错误配置 |
| **A06** | 易受攻击和过时的组件 (Vulnerable and Outdated Components) | 依赖的第三方组件存在已知漏洞 |
| **A07** | 身份识别和认证失败 (Identification and Authentication Failures) | 身份验证机制存在缺陷 |
| **A08** | 软件和数据完整性故障 (Software and Data Integrity Failures) | 未验证软件更新、CI/CD 管道完整性 |
| **A09** | 安全日志记录和监控故障 (Security Logging and Monitoring Failures) | 缺乏攻击检测和响应能力 |
| **A10** | 服务器端请求伪造 (SSRF) | 服务器端发起未授权的请求 |

> 与 2017 年版的对比：A01 从"注入"变为"失效的访问控制"，A04 新增"不安全的设计"，A08 合并了之前的不安全反序列化和 CI/CD 完整性议题，A10 从"不足的日志记录和监控"替换为 SSRF。

# A01: 失效的访问控制 (Broken Access Control)

## 概述

**访问控制 (Access Control)** 是将"谁可以做什么"这一策略强制执行在已认证用户身上的机制。当一个经过身份验证的用户可以执行超出其预期权限的操作时，就发生了**失效的访问控制**。这是 2021 年 OWASP Top 10 中排名最高的风险类别——它影响了 94% 的受测应用程序，且平均每个应用存在 3.81 个此类漏洞。

访问控制失效的本质是：**策略存在，但未得到正确执行**。不同于认证（"你是谁"）和授权（"你能做什么"的定义），访问控制是授权的**执行层面**——它确保代码中的每一次请求都被策略覆盖。

---

## 根本原因

失效的访问控制的根本原因可以从三个层面理解：

**1. 信任客户端的输入**

开发者默认假设用户只会访问他们"应该"访问的页面、点击他们"应该"点击的按钮、提交他们"应该"提交的参数。这种假设在安全模型中是根本错误的——攻击者会主动探测和篡改所有客户端可控的输入。

**2. 访问控制逻辑的分散与重复**

访问控制检查散布在多个端点、中间件、控制器中，而非集中在一个访问决策点。每当新增一个功能，开发者在"复制并修改"时就可能漏掉访问控制检查，或者复制了错误的检查逻辑。

**3. 对"隐蔽式安全"的依赖**

依赖以下假设来替代访问控制：
- URL 路径不可猜测（"管理员后台地址只有我知道"）
- 前端隐藏了按钮所以用户无法触发敏感操作
- API 端点未在文档中列出所以安全

这些假设都是无效的——攻击者通过枚举、逆向、抓包可以轻易发现这些隐藏的入口。

---

## 访问控制的三种基本类型

| 类型 | 含义 | 违反后果 |
|------|------|---------|
| **垂直访问控制** (Vertical) | 限制不同角色对功能的访问（如普通用户 vs 管理员） | 权限提升 (Privilege Escalation) |
| **水平访问控制** (Horizontal) | 限制同一角色用户对数据的访问（如同为普通用户，不能访问他人数据） | 越权访问 (IDOR) |
| **上下文相关的访问控制** (Context-dependent) | 限制多步骤流程中的操作顺序（如必须先支付才能下载） | 业务逻辑绕过 |

这三者覆盖了访问控制的全部维度。一个完全安全的应用必须正确实现所有三种。

---

## 失效访问控制的具体表现形式

### 1. 不安全的直接对象引用 (IDOR — Insecure Direct Object References)

**本质**：应用程序通过用户提供的参数直接访问内部对象（数据库记录、文件、功能），但未验证该用户是否有权访问该特定对象。

**核心特征**：URL 或请求参数中包含对象标识符（数字 ID、UUID、文件名），攻击者通过修改该标识符来访问其他用户的资源。

**典型案例**：

```
# 用户 A 访问自己的订单详情
GET /orders/12345

# 用户 A 修改 ID，访问用户 B 的订单
GET /orders/12346
```

**深层机制**：IDOR 并非一种独立的漏洞类型，而是水平访问控制缺失的**最典型表现形式**。其根因在于：引用（Reference）和授权（Authorization）在代码中是分离的——引用被存储为 URL 参数或表单字段，而授权逻辑可能根本不存在、在错误的粒度上运行、或依赖用户不会"知道"其他 ID 的假设。

**常见变体**：

| 变体 | 示例 | 说明 |
|------|------|------|
| 顺序 ID | `/users/1001/profile` | 自增主键，最易枚举 |
| UUID | `/files/d4f3a2b1-...` | 不可枚举但可从其他接口泄露 |
| 复合参数 | `?user_id=5&file=report.pdf` | 组合多个参数来定位对象 |
| 嵌套资源 | `/api/users/5/orders/42` | 需同时验证两级所有权 |
| 批量操作 | `DELETE /api/users` + body `{"ids":[1,2,3]}` | 批量请求中包含他人资源的 ID |

---

### 2. 缺少功能级访问控制 (Missing Function-Level Access Control)

**本质**：某个功能端点（API、页面、方法）完全没有访问控制检查，或检查仅在前端执行。

**典型案例**：

```
# 管理员功能：删除用户
POST /admin/users/delete
Body: {"user_id": 5}

# 普通用户直接向后端发送相同请求，后端未检查角色
# 导致普通用户也能执行管理员操作
```

**常见缺失位置**：
- 管理员面板下的所有子级 API 端点
- 批量操作、导入导出等"边缘功能"
- 开发/调试期间创建的临时端点
- 旧版 API（`/api/v1/`）在升级到 `v2` 后未下线
- WebSocket 和 GraphQL 端点——传统中间件可能不覆盖这些协议

**与前端的边界**：前端隐藏按钮（UI redaction）是可用性设计，不是安全控制。任何仅在前端实现的"访问控制"——如 React 中 `{isAdmin && <AdminPanel />}`——根本不构成访问控制，因为所有 JavaScript 逻辑运行在攻击者完全可控的环境中。

---

### 3. 路径遍历 / 强制浏览 (Forced Browsing)

**本质**：攻击者通过直接访问 URL 路径来发现和访问未被链接的页面或文件。

**典型场景**：

```
# 攻击者已知管理后台存在，但首页无入口链接
# 通过枚举常见路径来发现：
GET /admin
GET /manage
GET /backup
GET /.git/config
GET /wp-admin                    # 针对 WordPress
GET /actuator/env                # 针对 Spring Boot Actuator
GET /phpmyadmin
GET /api/swagger.json
```

**与目录遍历的区别**：强制浏览是访问"存在但不应该被访问的页面"，目录遍历是访问"文件系统上不应该被 Web 服务器公开的文件"。

**技术细节**：强制浏览依赖 Web 服务器或框架对 URL 的路由解析行为。某些框架（如 Spring Boot）默认暴露了丰富的管理端点（`/actuator`），开发者可能仅移除首页链接而忘记禁用端点本身。

---

### 4. 参数篡改 (Parameter Tampering)

**本质**：攻击者修改客户端发送到服务器的参数以绕过访问控制。

**典型攻击面**：

| 参数位置 | 示例 | 风险 |
|----------|------|------|
| URL 查询参数 | `?role=admin` | 权限依赖客户端角色声明 |
| POST body 字段 | `{"is_admin": true}` | 批量赋值 (Mass Assignment) |
| Cookie | `user_role=premium` | 信任客户端存储的权限信息 |
| Header | `X-Original-User: admin` | 反向代理的原始用户标识被伪造 |
| Hidden form field | `<input type="hidden" name="price" value="99">` | 价格/权限等关键值在隐藏字段中 |

**批量赋值 (Mass Assignment) 的深层原理**：

```python
# Flask/Laravel/Spring 等框架允许一次性绑定请求参数到模型
@router.put("/users/{id}")
def update_user(id: int, data: UserUpdate):
    user = db.query(User).get(id)
    # 危险：如果 UserUpdate 包含 is_admin 字段且未加保护
    for key, value in data.dict().items():
        setattr(user, key, value)
    db.commit()
```

攻击者可以在请求 body 中添加 `"is_admin": true`。如果模型或 DTO 未使用白名单限制可更新字段，该值会被直接写入数据库。解决方式是使用显式字段白名单或 `exclude` 声明敏感字段。

### 5. CORS 配置缺陷导致的访问控制绕过

**本质**：跨域资源共享（CORS）的配置错误使得恶意网站可以代表已认证用户向目标应用发起跨域请求并读取响应。

**访问控制层面的问题**：CORS 是一种**基于浏览器同源策略的放松机制**。当 CORS 配置过于宽松，攻击者的恶意网站可以：
1. 利用用户浏览器中已有的 session cookie（`withCredentials: true`）
2. 向目标应用发起 GET/POST 请求
3. 读取响应内容

**危险配置**：

```
# 反射式 Origin（极度危险）
Access-Control-Allow-Origin: null         # 接受 null origin（iframe sandbox, data: URL）
Access-Control-Allow-Origin: *            # 通配符 + credentials 在某些实现下有安全隐患

# 危险：将请求中的 Origin 直接反射回 ACAO header
# 服务端代码：response.setHeader("Access-Control-Allow-Origin", request.getHeader("Origin"))
Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Credentials: true
```

**相关概念区分**：CORS 配置缺陷是**访问控制失效的一种特殊形式**——它涉及跨域资源访问的策略配置，而非应用本身的功能级或数据级访问控制。它常被列为独立的漏洞类别，但在 OWASP 分类中归入 A01。

### 6. JWT 令牌操控

**本质**：应用程序依赖 JWT 中的声明（claims）做访问控制决策，但未正确验证令牌的完整性和来源。

**具体表现**：

| 攻击方式 | 原理 | 利用条件 |
|----------|------|---------|
| 算法混淆 | 将 `alg` 改为 `none`，服务器跳过签名验证 | 服务器信任 JWT header 中的算法声明 |
| 密钥混淆 | 使用服务器的公钥（从 JWKS 端点获取）作为 HMAC 密钥签名 | 服务器使用同一密钥做 HMAC 和 RSA 验证 |
| Claim 篡改 | 直接修改 payload 中的 `role` 字段后重放 | 服务器未验证签名或签名验证有缺陷 |
| 未验证 kid/jku | 篡改 header 中的 kid 指向攻击者控制的密钥 | 服务器按 kid 获取验证密钥且未限制来源 |

**技术细节**：JWT 访问控制的脆弱性根源于 **信任边界模糊**——令牌由客户端持有和提交，服务器必须依赖客户端提供的令牌来决定该客户端的权限。一旦验证机制存在任何缺陷，整个访问控制体系就崩塌。

**防御要点**：
- 始终显式指定期望的算法（`verify(token, key, algorithms=["RS256"])`）
- 对 kid 做白名单校验
- 限��令牌有效期（短 TTL + refresh token 轮换）
- 权限变更后立即使令牌失效（维护令牌黑名单或版本号）

### 7. 目录遍历 (Directory Traversal / Path Traversal)

**本质**：应用程序使用用户输入构造文件系统路径时未充分验证，导致攻击者可以通过 `../` 序列访问 Web 根目录之外的文件。

**与访问控制的关联**：目录遍历本质上是**文件系统级别的访问控制失效**——应用程序的文件读取/写入操作没有限制在授权目录范围内。

**典型攻击**：

```
# 原始请求：读取用户头像
GET /download?file=avatar.png

# 攻击：读取 /etc/passwd
GET /download?file=../../../../etc/passwd

# 编码绕过
GET /download?file=%2e%2e%2f%2e%2e%2fetc%2fpasswd
GET /download?file=....//....//etc/passwd          # 简单过滤 ../ 的绕过
```

**语言/框架差异**：

| 环境 | 风险函数 | 防御方法 |
|------|---------|---------|
| Python | `open(user_input)` | `os.path.abspath()` + 前缀检查 |
| PHP | `include $_GET['page']` | `basename()` + 白名单 |
| Java | `new File(basePath, userInput)` | `getCanonicalPath()` 后验证路径前缀 |
| Node.js | `fs.readFile(userPath)` | `path.resolve()` + 前缀检查 |

**关键注意点**：`getCanonicalPath()`（Java）或 `realpath()`（PHP/C）必须先调用以解析符号链接和 `../`，再进行前缀检查。如果检查顺序错误（先检查前缀再规范化），攻击者可以用符号链接绕过。

---

### 8. 基于时间的访问控制绕过

**本质**：访问控制决策依赖时间或状态，但这些状态可被攻击者操控或预测。

**具体场景**：
- 密码重置 token 未设置有效期限或过期时间过长
- 一次性邀请链接可在使用后多次访问
- 账户注销后的冷却期内资源仍可被访问
- 竞态条件：在权限回收完成前快速发起请求
- "先支付，后下载"的业务流中，后端在支付完成前就返回了下载 token

---

### 9. 多步骤流程中的访问控制缺失

**本质**：对于需要多步骤完成的敏感操作，中间步骤缺少访问控制检查，或各步骤的授权状态不一致。

**典型案例**：

```
# 银行转账三步流程
# Step 1: POST /transfer/init    → 验证了
# Step 2: POST /transfer/confirm → 未独立验证（假设只有通过 Step 1 才会到达）
# Step 3: POST /transfer/execute → 未独立验证

# 攻击者直接请求 Step 2 或 Step 3，跳过前置验证
```

**根本原因**：开发者假设工作流的状态转换只能按预期路径发生，但 HTTP 请求的本质是无状态——每个端点的每次调用都必须独立验证。

## 检测方法

### 人工检测

1. **角色矩阵测试**：为每个角色创建账号，系统性地访问所有功能端点，记录预期允许/拒绝与实际行为的差异
2. **参数枚举**：对数值型标识符（ID、order_id 等）遍历测试，确认是否存在水平越权
3. **请求重放**：用低权限用户的 session/token 重放高权限用户的敏感请求
4. **参数注入**：在请求中添加 `role=admin`、`is_admin=true` 等字段测试批量赋值

### 自动化检测

- 请求/响应差异分析（同一请求，不同用户身份，响应是否不同）
- SAST（静态分析）：检测端点是否缺少授权注解/装饰器
- DAST（动态扫描）：爬取 + 角色化请求重放
- 访问控制矩阵的单元测试（针对每个端点编写授权测试用例）

### 访问控制测试的难点

访问控制的自动化检测比其他漏洞类型更难，因为：
- 不存在通用的"访问控制是否正确的签名"——需要理解业务语义
- 误判率极高（功能设计上的正常行为可能被标记为漏洞）
- 需要多角色多用户的多维矩阵测试

## 防御方案

### 1. 默认拒绝 (Deny by Default)

**原理**：除非显式授予访问权限，否则一律拒绝。这是安全工程中最基本的原则之一，但在 Web 应用中常被忽视。

**实施**：
- 所有新端点默认需要认证和基础角色授权
- 使用声明式授权注解（`@PreAuthorize`、`[Authorize]`、`@require_role`）
- 全局中间件拦截所有请求并检查授权，而非每个端点手动调用

**局限性**：需要维护一个精确的权限矩阵。如果权限定义松散（如几乎所有用户都有 `user` 角色且大多数端点只需要 `user`），默认拒绝的效果接近默认允许。

---

### 2. 基于资源的所有权验证

**原理**：不依赖单一的"角色检查"，而是在每次数据访问时验证调用者是否为该资源的所有者。

**实施**：
```java
// 错误：仅检查角色
@PreAuthorize("hasRole('USER')")
public Order getOrder(Long orderId) { ... }

// 正确：检查资源所有权
@PreAuthorize("hasRole('USER') and @orderService.isOwner(#orderId, principal.id)")
public Order getOrder(Long orderId) { ... }
```

**局限性**：所有权检查需要考虑资源之间的层级关系（如用户→订单→订单项），以及共享资源（如团队成员共享文档）的复杂权限模型。

---

### 3. 使用不可预测的标识符

**原理**：将自增 ID 替换为随机生成的 UUID 或不透明引用，增加枚举的难度。

**实施**：使用 UUID v4 或 crypto-random 标识符替代自增主键。

**局限性（重要）**：**这不能替代访问控制**——仅增加枚举难度，属于纵深防御的辅助措施。UUID 可能通过其他渠道泄露（API 响应、日志、Referer header、分享链接），一旦泄露，没有访问控制的应用仍然不安全。

---

### 4. 集中化的访问控制架构

**原理**：将所有访问控制决策集中到单一的授权模块中，避免逻辑分散带来的遗漏。

**实施**：
- 使用成熟的授权框架（Spring Security、Casbin、OPA）
- 定义声明式的权限策略文件，而非在代码中硬编码
- 对所有 API 网关流量施加统一的授权检查
- 访问控制逻辑放在中间件层，业务代码不需关��授权

**局限性**：粒度可能不够——集中策略难以覆盖复杂的、上下文相关的业务授权逻辑（如"只有订单创建者且订单状态为草稿才能修改"）。

---

### 5. 服务端无状态 + Token 验证

**原理**：任何来自客户端的权限声明都不被信任。权限信息由服务端在每次请求时从服务器权威数据源（数据库/缓存）中加载。

**实施**：
- JWT 中仅存储用户标识（`sub`），不存储角色/权限
- 每次请求通过用户标识从服务端获取当前权限
- Token 签名验证使用白名单算法

**局限性**：性能开销（每次请求需要查询权限数据），需要配合缓存缓解。

---

### 6. 多步骤流程的状态完整性

**原理**：每个步骤独立验证用户身份、资源所有权和流程状态。

**实施**：
- 工作流状态存储在服务端（服务端 Session 或数据库）
- 每个步骤验证当前用户是否有权执行该操作
- 每个步骤验证该资源是否处于允许该操作的状态
- 使用 Anti-CSRF token 防止跨站提交

---

### 7. 日志与监控

**原理**：记录所有访问控制失败事件，作为检测攻击和事后审计的依据。

**实施**：
- 记录每次 403 Forbidden（包含用户 ID、目标资源、时间戳）
- 对同一用户的连续拒绝设置告警阈值
- 对资源 ID 的快速枚举建立速率限制
