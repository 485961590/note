## 用户名枚举
系统通过不同反馈暴露账号是否存在。

曾经常见现在应该不常见了：
- 用户名错和密码错提示不同；
- 响应长度、响应内容或状态码有细微差异；
- 正确用户名和错误用户名响应时间不同（可以加长密码，增加正常用户名校验密码的时间更明显）；
- 已存在账号会被限速或暂时封禁，不存在账号不会（也就是只封禁存在的用户名）。
**这样可以极大的缩短暴力破解的时间，不用用户名与密码的笛卡尔积，攻击者可以先确认有效用户名，再进行密码攻击。**

## 暴力破解防护失效
系统没有正确限制登录尝试，或者限制方式容易绕过。

包括：
- 没有失败次数计数器；
- 只按 IP 限制，攻击者可以更换 IP；
- 信任用户提供的 `X-Forwarded-For`，导致 IP 限制被伪造；
- 登录成功后错误次数被重置，攻击者可以用自己的账号定期成功登录来清零计数（每几次错误尝试后固定一个成功账户用于重置计数器）；
- 只限制单个账号，攻击者可以轮换多个账号。

**限制机制的维度和状态管理的不正确**

## 账户锁定机制绕过
账户锁定本身存在，但设计不合理。

例如：
- **密码喷洒**：少量常见密码，轮流尝试大量用户名；
- **撞库**：每个泄露账号密码组合只尝试一次，因此不容易触发**单账号**锁定；
- 通过低频、分散的尝试避开次数限制；
- 诱发大量错误登录，让正常用户被封号，造成拒绝服务。

**防护争对的是账号本体而非发起攻击的人，应该把封禁放在封禁攻击者IP上，而非单个账号**

## 弱认证协议
HTTP Basic Authentication 的问题不主要是“能不能爆破”，而是认证凭据本身过于简单：
- 用户名和密码只是 Base64 编码，不是加密；
- 每次请求都重复发送同一组凭据；
- 凭据容易被重放；
- 通常没有完善的暴力破解防护；
- 浏览器会自动携带认证信息，可能产生 CSRF 风险；
- 用户容易在其他系统重复使用相同密码。

# 攻击方式的分类

**暴力破解**：     一个账号尝试大量密码
**密码喷洒**：     少量常见密码尝试大量账号
**撞库**：            使用外部泄露的真实账号密码组合
**用户名枚举**：  先判断哪些账号存在
**时间侧信道**：  根据响应时间差异判断账号是否有效
