# File Path Traversal（文件路径穿越）

> **参考主线：** [PortSwigger Academy：File path traversal](https://portswigger.net/web-security/file-path-traversal) | [Path traversal learning path](https://portswigger.net/web-security/learning-paths/path-traversal)
>
> **关联概念：** [[Server-Side Request Forgery (SSRF)]] | [[XML External Entity (XXE)]] | [[Input Validation]]
>
> **测试范围：** 以下示例用于 PortSwigger Web Security Academy、CTF 或明确授权的本地测试环境。重点是建立“输入点 → 路径处理 → 文件操作 → 可观察结果”的分析方法，而不是机械记忆 payload。

---

## 一、先记住核心思路

文件路径穿越（File Path Traversal，也称 Directory Traversal）不是“某个字符串没有过滤”这么简单，它的本质是：

> **应用程序把攻击者可控的数据，当成了文件系统路径的一部分，并在没有建立可靠目录边界的情况下交给文件读取、写入、删除或加载 API。**

分析一个疑似文件路径穿越点时，始终沿着下面的链路思考：

```text
HTTP 请求中的可控输入
        |
        v
参数解码、拼接、过滤、规范化
        |
        v
最终传给文件系统 API 的路径
        |
        v
读取 / 写入 / 删除 / 加载文件
        |
        v
响应内容、状态码、错误信息或业务行为
```

真正需要回答的不是“`../` 能不能用”，而是：

1. **哪个输入控制了路径，控制的是完整路径还是文件名的一部分？**
2. **应用在什么阶段进行 URL 解码、过滤和路径规范化？**
3. **过滤发生在规范化之前还是之后？**
4. **最终路径是否仍然位于预期目录内？**
5. **文件操作的结果能否通过响应或业务行为观察到？**

这五个问题比背诵某个固定 payload 更重要。

## 二、什么是文件路径穿越？

### 2.1 正常的文件读取功能

很多应用会根据请求参数返回图片、附件、模板或下载文件，例如：

```http
GET /image?filename=218.png HTTP/1.1
Host: vulnerable-website.com
```

服务端可能存在类似逻辑：

```text
读取 /var/www/images/218.png
将文件内容作为 HTTP 响应返回
```

如果 `filename` 只是一个由服务端生成的文件 ID，风险较低；如果它可以直接影响文件系统路径，就需要继续追踪。

### 2.2 穿越发生的原因

攻击者利用路径中的特殊组成部分改变解析结果：

- Unix/Linux 常见目录分隔符：`/`
- Windows 常见目录分隔符：`\`，部分组件也接受 `/`
- 父目录表示：`..`
- 当前目录表示：`.`
- Unix/Linux 绝对路径通常以 `/` 开头
- Windows 绝对路径可能以盘符开头，例如 `C:\`，也可能使用 UNC 路径

例如，应用原本期望读取：

```text
/var/www/images/218.png
```

如果它直接把用户输入拼接到目录后面：

```text
/var/www/images/../../../etc/passwd
```

文件系统规范化后，路径可能等价于：

```text
/etc/passwd
```

这里的关键不是“字符串中出现了三个 `../`”，而是**应用最终交给文件系统解析的规范路径逃出了预期目录**。

## 三、先区分“文件名参数”和“路径参数”

同一个参数名不代表同一种风险。测试前先判断输入在路径中的位置。

| 输入形态 | 示例 | 首要问题 |
|---|---|---|
| 完整文件名 | `filename=218.png` | 是否能将文件名替换为其他路径？ |
| 相对路径 | `filename=images/218.png` | 分隔符是否被接受？基准目录是什么？ |
| 目录前缀 + 文件名 | `filename=/var/www/images/218.png` | 是否能利用 `..` 退回上级目录？ |
| 固定前缀 + 用户输入 | `'/var/www/images/' + filename` | 校验是在拼接前还是规范化后？ |
| 用户输入 + 固定后缀 | `filename=<input>.png` | 是否存在扩展名检查？检查发生在哪一层？ |
| 下载或导出路径 | `download?path=...` | 是否不仅能读，还能影响写入或删除位置？ |
| 模板、语言包、日志等加载参数 | `template=...` | 文件内容是否会被解释、执行或二次解析？ |

优先记录以下信息：

```text
参数名称：filename
出现位置：查询参数 / POST 参数 / JSON / Cookie / Header / 路径片段
原始值：218.png
服务端表现：返回图片，Content-Type 为 image/png
推测操作：将参数拼接到某个图片目录后调用文件读取 API
```

不要看到“图片接口”就只测试图片；很多路径穿越点隐藏在下载、预览、导入、语言切换、模板选择和日志查看功能中。

## 四、系统化测试流程

### 4.1 第一步：建立基准请求

先发送一个完全正常的请求，记录：

- HTTP 方法和路径
- 参数名称及原始值
- 响应状态码
- 响应长度
- `Content-Type`
- 文件内容或页面中的可见特征
- 是否存在缓存、重定向或错误信息

例如：

```http
GET /image?filename=218.png HTTP/1.1
Host: lab-id.web-security-academy.net
```

```text
响应：200 OK
Content-Type：image/png
响应长度：若干字节
```

基准请求的价值在于：之后每次只改变一个因素，才能知道是哪一步导致了响应变化。直接连续尝试大量编码形式，容易把“过滤失败”“文件不存在”和“请求被服务器拒绝”混为一谈。

### 4.2 第二步：确认是否确实控制了文件路径

可以先把文件名换成另一个已知存在、但不会造成破坏的文件名，观察响应是否随输入变化。

随后再观察异常输入的行为：

| 观察结果 | 可能含义 |
|---|---|
| 文件内容随文件名改变 | 输入很可能进入了文件读取路径 |
| 所有输入都返回同一图片 | 参数可能被忽略、被映射为 ID，或响应被缓存 |
| 返回统一的“文件不存在” | 输入可能到达读取点，但目标路径不存在 |
| 400/403 且响应明显不同 | 可能存在输入验证或 WAF 规则 |
| 500 并出现文件系统错误 | 可能泄露了路径处理过程或应用工作目录 |

这一步只回答“输入是否影响文件操作”，还不能证明存在路径穿越。

### 4.3 第三步：使用相对路径验证目录边界

在授权靶场中，使用题目明确允许的已知系统文件作为验证目标。Linux 环境常见验证对象是 `/etc/passwd`，Windows 环境常见验证对象是 `C:\Windows\win.ini`；实际环境应根据目标系统和实验说明选择，不要假定服务器一定是 Linux。

相对路径的基本思路是：

```text
从当前文件所在目录开始
向上退回一层或多层
再进入目标文件所在目录
```

Linux 风格示意：

```text
../../../etc/passwd
```

Windows 风格示意：

```text
..\..\..\Windows\win.ini
```

向上层级不是固定数字。需要根据应用的基准目录推断，并通过响应逐步确认。层级过少时，目标文件仍然位于错误目录；层级足够多时，某些文件系统会停留在根目录，不会因为继续使用 `..` 而产生新的目录。

### 4.4 第四步：判断是“路径逃逸”还是“文件不存在”

读取失败不等于不存在漏洞。至少区分以下情况：

```text
输入被过滤        -> 请求被拒绝或被改写
路径解析成功但文件不存在 -> 404、空响应或统一错误
路径解析成功且文件可读   -> 返回目标文件内容
文件存在但无权限         -> permission denied、403 或统一错误
应用不回显内容           -> 需要使用间接信号判断
```

判断时应同时看状态码、响应长度、错误模板、`Content-Type` 和业务行为，不能只看页面上有没有明显的文件内容。

### 4.5 第五步：一次只改变一个解析变量

推荐按下面的顺序排查：

```text
原始相对路径
  -> 改变 ../ 的层级
  -> 尝试绝对路径
  -> 尝试目标平台的另一种分隔符
  -> 检查 URL 编码层数
  -> 检查前缀校验位置
  -> 检查非递归删除
  -> 最后分析后缀和历史兼容行为
```

每次请求都记录：

```text
输入形式：
服务端是否解码：
过滤前的值：
过滤后的值（若可观察）：
规范化后的推测路径：
响应差异：
结论：
```

这种记录方式能把“尝试 payload”变成“验证假设”。

## 五、常见限制与对应思路

### 5.1 绝对路径可用时，不必执着于 `../`

有些应用允许用户提供一个完整路径，或只检查文件名是否存在，并没有限制路径必须位于某个目录。此时可以直接从目标平台的绝对路径思考：

```text
Linux：/etc/passwd
Windows：C:\Windows\win.ini
```

这类情况的思路是：

```text
相对路径尝试失败
        |
        v
确认应用是否接受绝对路径
        |
        v
判断绝对路径是否绕过了相对路径过滤
```

如果服务端使用了可靠的“固定根目录 + 规范化路径 + 目录边界校验”，绝对路径通常会被拒绝；如果只是简单地在字符串中查找 `../`，则绝对路径可能成为另一条路径。

相关实验：[File path traversal, traversal sequences blocked with absolute path bypass](https://portswigger.net/web-security/file-path-traversal/lab-absolute-path-bypass)

### 5.2 非递归删除：过滤器只处理了一次

常见的错误防御是：发现输入中包含 `../` 后，用字符串替换将其删除一次。

问题在于，替换本身可能改变字符串结构，而程序不会再次检查新形成的内容。嵌套序列可能因此在一次过滤后仍留下可解析的穿越结构。

典型思路示意：

```text
原始输入：构造一层“外壳”，其中包含被过滤的穿越片段
一次替换：外层字符被删除或拼接
剩余结果：重新形成 ../ 或等价的路径结构
文件系统：对最终路径进行规范化
```

PortSwigger 实验中使用了类似 `....//` 的嵌套形式。这里应记住的是**过滤算法的处理次数和处理顺序**，不是死记某一个字符串；不同语言的替换函数、正则表达式和路径解析器可能产生不同结果。

相关实验：[File path traversal, traversal sequences stripped non-recursively](https://portswigger.net/web-security/file-path-traversal/lab-sequences-stripped-non-recursively)

### 5.3 URL 编码：过滤层和文件系统层看到的不是同一个值

HTTP 请求中的路径参数通常会经历一个或多个解码阶段：

```text
浏览器或工具编码
        |
        v
Web 服务器解码
        |
        v
框架或路由层再次解码
        |
        v
应用过滤
        |
        v
文件系统路径解析
```

如果过滤器在第一次解码前后的位置设计不当，就可能出现：

- 过滤器检查的是编码形式，文件系统得到的是解码后的分隔符
- 第一次解码得到第二次编码，后续组件再解码为真正的 `../`
- 代理、Web 服务器、框架和应用对编码处理不一致

双重编码的分析方法是：

```text
先写出发送时的字节序列
再逐层还原每一次解码结果
确定哪一层执行过滤
最后判断文件系统看到的最终字符串
```

相关实验：[File path traversal, traversal sequences stripped with superfluous URL-decode](https://portswigger.net/web-security/file-path-traversal/lab-superfluous-url-decode)

> 编码不是万能绕过。只有在“解码顺序”和“过滤位置”恰好形成差异时才有意义；如果应用先规范化、再做目录边界校验，多重编码不会改变安全结论。

### 5.4 验证路径开头：检查原始字符串而不是规范路径

另一种常见逻辑是要求输入必须以某个目录开头，例如：

```text
if filename starts with /var/www/images/:
    读取 filename
```

如果校验只比较原始字符串，而没有在规范化后重新确认目录边界，下面的逻辑风险就会出现：

```text
原始字符串看起来：/var/www/images/../../../etc/passwd
前缀检查：通过
规范化之后：/etc/passwd
实际位置：已离开 /var/www/images/
```

这里的核心判断是：

> **“字符串以某个前缀开头”不等于“规范化后的路径位于该目录内”。**

相关实验：[File path traversal, validation of start of path](https://portswigger.net/web-security/file-path-traversal/lab-validate-start-of-path)

### 5.5 固定后缀：区分“字符串拼接”和“文件系统解析”

有些应用会把用户输入和固定扩展名拼接：

```text
读取 /var/www/images/ + user_input + .png
```

此时要先弄清楚后缀是：

- 在过滤之前拼接
- 在过滤之后拼接
- 作为路径的一部分交给高层库
- 被拆分、截断或转换后再交给底层系统 API

历史上的某些 C 风格 API 会把 NUL 字节视为字符串结束符，因此曾出现“让检查逻辑看到 `.png`，让底层 API 提前结束路径”的问题。但这依赖具体语言、运行时、库版本和数据转换过程；现代框架和 API 通常会拒绝 NUL 字节，不能把它当作通用技巧。

相关实验：[File path traversal, validation of file extension with null byte bypass](https://portswigger.net/web-security/file-path-traversal/lab-validate-file-extension-null-byte-bypass)

正确的分析方式不是直接假设后缀可绕过，而是画出实际数据流：

```text
HTTP 参数
  -> URL 解码
  -> 输入验证
  -> 拼接 .png
  -> 路径规范化
  -> 文件 API
```

只要其中任一阶段拒绝危险输入，后续形式就不会成立。

### 5.6 分隔符差异：不要只测试一种平台

| 环境或组件 | 需要关注的路径形式 |
|---|---|
| Linux/Unix | `/`、`..`、绝对路径 `/etc/passwd` |
| Windows | `\`、`/`、盘符路径、UNC 路径 |
| 跨平台框架 | 框架可能先统一分隔符，再交给操作系统 |
| 归档或虚拟文件系统 | 文件名可能由库自行解析，不完全等同于宿主机路径 |
| 容器环境 | 路径穿越可能只影响容器文件系统，但容器内的配置和凭据仍可能敏感 |

平台判断可以来自错误信息、响应头、实验说明、应用技术栈或已知文件格式，但不要仅凭页面外观猜测操作系统。

## 六、从“回显内容”扩展到“可观察信号”

### 6.1 有回显：确认内容和上下文

当接口直接返回文件内容时，重点记录：

- 文件内容是否完整
- 是否被编码或截断
- 响应的 `Content-Type` 是否改变
- 文件内容是否被当作 HTML、JSON、图片或模板处理
- 是否存在二次解析或模板执行

“能读到文件”只是第一层结论。若读取结果会被模板引擎、XML 解析器、脚本解释器或图片处理库进一步处理，影响面可能不同。

### 6.2 无回显：利用间接差异建立判断

盲文件读取或受限文件读取中，不能把“页面没有显示内容”当作“没有漏洞”。可以观察：

| 信号 | 分析价值 | 局限 |
|---|---|---|
| 状态码 | 区分拒绝、存在、错误 | 应用可能统一返回状态码 |
| 响应长度 | 文件内容不同可能导致长度变化 | 压缩、模板和缓存会干扰 |
| 响应时间 | 大小、权限或处理路径不同可能产生差异 | 网络抖动和缓存容易误判 |
| 错误类型 | 暴露路径、权限和解析阶段 | 生产环境通常会统一错误 |
| `Content-Type` | 反映应用如何识别目标文件 | 可能由固定路由强制设置 |
| 业务状态 | 下载计数、预览状态、缓存键变化 | 需要理解应用流程 |

建议使用多个独立信号交叉验证，不要只凭一次长度或时间差下结论。

### 6.3 文件读取与其他漏洞的关系

文件路径穿越常常是攻击链中的一个环节：

```text
路径穿越读取配置文件
        |
        v
获得数据库连接信息或应用密钥
        |
        v
进一步访问数据库、对象存储或内部服务
```

可能关联：

- **SSRF**：两者都涉及访问应用本不应访问的资源，但 SSRF 的目标通常是网络地址，路径穿越的目标是文件系统路径。
- **XXE**：XXE 可能成为读取本地文件或发起后端请求的入口，但根因是 XML 解析器对外部实体的处理。
- **任意文件上传**：上传和路径穿越结合时，可能影响文件写入位置或后续加载位置。
- **本地文件包含（LFI）**：某些动态语言将读取的文件作为代码或模板加载时，文件路径穿越可能升级为代码执行；是否成立取决于加载 API 和文件内容。
- **权限配置错误**：路径穿越本身不等于能够读取任意文件，文件系统权限仍决定最终影响。

不要因为“读取到了文件”就直接推断“可以执行代码”；必须继续分析文件操作 API 的语义。

## 七、一个适合靶场的分析记录模板

每个 Lab 或真实授权测试都可以单独记录一行假设，再逐步验证：

```markdown
### 案例：<功能名称>

- 请求：`GET /<path>?<parameter>=<value>`
- 可控输入：`<parameter>`
- 正常行为：<返回什么文件或页面>
- 推测文件操作：<读取 / 写入 / 删除 / 加载>
- 基准响应：<状态码、长度、Content-Type、内容特征>
- 第一假设：<输入是否直接作为路径>
- 验证结果：<响应差异>
- 过滤位置：<已知或推测的解码、过滤、规范化顺序>
- 目录边界：<是否仍在预期目录内>
- 权限边界：<目标文件是否可读>
- 最终结论：<漏洞成立 / 输入被安全映射 / 证据不足>
```

### 思路示例

```text
1. 看到 filename 参数能够改变返回的图片
2. 推断 filename 可能进入文件读取路径
3. 先用正常文件名建立响应基准
4. 使用授权实验中的已知文件验证读取能力
5. 若相对路径失败，区分过滤失败与目标不存在
6. 分析应用是否接受绝对路径、另一种分隔符或编码后的值
7. 如果存在固定目录前缀，检查校验是在规范化前还是后
8. 如果存在固定后缀，追踪后缀拼接和底层 API 的处理
9. 用多个响应信号确认结果
10. 回到根因：最终路径是否有可靠的目录边界
```

---

## 八、根本原因分析

### 8.1 数据与路径语义混在一起

最常见的危险模式是：

```text
固定目录 + 用户输入 = 文件系统路径
```

开发者以为用户输入只是“文件名”，但文件系统会继续解释其中的目录分隔符、父目录和绝对路径。只要输入仍保留路径语义，它就不是普通文件名。

### 8.2 在错误的表示层做校验

路径至少有几个不同表示层：

```text
HTTP 原始字节
  -> URL 解码后的字符串
  -> 应用过滤后的字符串
  -> 路径库解析后的路径
  -> 文件系统实际访问的对象
```

在早期表示层检查一个字符串，不能自动证明后续表示层仍然安全。尤其要警惕：

- 先检查、后解码
- 先检查、后拼接
- 先检查字符串前缀、后规范化
- 只删除一次危险片段
- 不同组件重复解码

### 8.3 权限边界没有配合路径边界

即使应用允许路径逃逸，攻击者能读到什么仍受进程权限、容器隔离、文件 ACL 和运行环境影响。因此评估影响时要分开写：

```text
路径控制能力：是否能指定预期目录之外的路径
文件权限能力：进程身份是否有权访问该路径
内容影响：文件是否包含凭据、密钥或可执行配置
```

不要把“存在路径穿越”和“读取所有系统文件”当成同一个结论。

---

## 九、防御方案：从根本上消除路径语义

### 9.1 最推荐：使用服务端文件 ID 映射

如果业务只需要访问一组受控文件，不要让客户端提交文件系统路径：

```text
客户端提交：file_id=218
        |
        v
服务端查询数据库或内存映射
        |
        v
得到服务端保存的固定文件路径
```

例如：

```text
218 -> /var/www/images/218.png
```

客户端永远不知道也不能决定实际路径。这比在用户输入上不断增加黑名单更可靠。

### 9.2 必须接受路径时：规范化后做目录边界校验

安全流程应当是：

```text
1. 选定服务端允许访问的固定根目录
2. 将用户输入解析为路径
3. 对路径进行规范化或 canonicalization
4. 判断规范化后的路径是否仍位于固定根目录之内
5. 再执行文件操作
```

目录边界比较不能只使用简单的字符串前缀。例如：

```text
允许目录：/srv/app/data
危险相似目录：/srv/app/data-backup
```

`startsWith("/srv/app/data")` 会把后者也误认为在允许目录内。比较时应使用路径库提供的相对路径判断，或确保前缀后紧跟目录分隔符。

伪代码：

```text
base = canonicalize(允许目录)
target = canonicalize(join(base, userInput))

if target 不在 base 目录及其子目录内:
    拒绝请求
else:
    执行文件操作
```

不同语言的路径 API 行为不同，必须查阅对应运行时文档；不要把伪代码直接当成某种语言的完整安全实现。

### 9.3 文件名白名单是补充，不是替代

如果业务只允许有限格式，可以限制：

- 文件 ID 或固定字符集
- 文件名长度
- 允许的扩展名
- 不允许路径分隔符、控制字符和 NUL
- 不允许绝对路径

但扩展名检查本身不能证明安全：

- 文件名可能包含路径分隔符
- 编码和解码可能发生在检查之后
- 大小写、Unicode、备用分隔符可能造成差异
- 文件内容的真实类型可能与扩展名不同

因此白名单应与规范化后的目录边界校验同时使用。

### 9.4 最小权限与隔离

即使应用代码出现缺陷，也应限制进程可访问的文件范围：

- 使用专用低权限账户运行服务
- 只授予应用目录所需的读取或写入权限
- 将密钥、配置和用户上传目录分离
- 使用容器、沙箱或操作系统 MAC 机制降低横向影响
- 对下载目录和模板目录进行不同权限隔离

这属于纵深防御，不能替代代码层面的路径校验。

### 9.5 错误处理与日志

对外返回统一的错误信息，避免泄露：

- 服务器真实工作目录
- 操作系统路径格式
- 用户名、框架目录和依赖版本
- 权限错误的详细原因

内部日志仍应记录足够的安全审计信息，例如请求 ID、被拒绝的参数类型和规范化结果摘要，但不要把敏感文件内容写入普通日志。

## 十、常见错误防御

| 错误防御 | 为什么不可靠 |
|---|---|
| 只过滤 `../` | 没有处理绝对路径、反斜杠、编码和规范化顺序 |
| 只检查原始字符串前缀 | 规范化后路径可能已经逃出目录 |
| 只检查扩展名 | 文件名仍可能包含路径语义，且检查和使用可能处于不同解码层 |
| 用字符串替换删除一次 | 非递归处理可能留下新的穿越结构 |
| 依赖 WAF 黑名单 | WAF 不一定理解应用和文件系统的最终解析结果 |
| 认为 URL 编码自动安全 | 解码可能发生多次，且发生在过滤之后 |
| 只依赖当前运行用户权限 | 权限变化、容器配置或挂载可能改变影响范围 |
| 读取失败就认为没有漏洞 | 可能只是文件不存在、无回显或错误被统一处理 |

根本性修复始终是：**客户端提交标识符，服务端决定路径；如果必须接收路径，则在规范化后执行严格的目录边界校验。**

## 十二、与相近概念的区别

| 概念 | 主要被控制的资源 | 典型问题 |
|---|---|---|
| 文件路径穿越 | 服务器文件系统路径 | 访问预期目录之外的文件或文件操作目标 |
| LFI | 本地文件加载/包含机制 | 文件内容可能被解释为代码或模板 |
| 任意文件读取 | 文件读取权限范围 | 不一定通过 `..`，也可能是 IDOR、绝对路径或错误映射 |
| SSRF | 网络 URL 或后端网络请求 | 访问内网服务、云元数据或其他网络资源 |
| XXE | XML 解析器的外部实体 | 借助 XML 外部实体读取文件或发起请求 |
| 任意文件写入 | 文件写入目标 | 可能覆盖配置、上传脚本或写入敏感目录 |

判断漏洞类型时，应根据**实际 sink 和最终资源**命名，而不是只根据某个 payload 命名。

---

## 十三、一句话总结

> **文件路径穿越的核心不是寻找“神奇字符串”，而是还原应用对路径的完整处理链：输入经过几次解码、如何拼接和过滤、何时规范化，以及规范化后的最终路径是否仍被可靠地限制在允许目录内。**
