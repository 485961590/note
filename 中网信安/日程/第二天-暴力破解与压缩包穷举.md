# 第二天：暴力破解与压缩包穷举攻击

## 核心概念

今天的内容分为两大板块，本质上都属于**穷举攻击（Brute Force / Exhaustive Attack）**：

| 板块 | 目标 | 主力工具 |
|------|------|----------|
| Web 登录站点暴力破解 | 绕过登录认证 | Burp Suite（主力）、Hydra、其它集成工具 |
| 压缩包密码破解 | 破解 ZIP / RAR 加密 | John the Ripper (jumbo) + Hashcat |

---

## 一、Web 登录站点暴力破解

### 1.1 无防护 — 基础爆破

- 使用 Burp Suite 抓取登录请求
- 发送到 Intruder 模块，标记密码（或用户名）参数为 payload
- 载入字典，直接跑

> 没有额外防护手段时，唯一的变量就是字典质量与请求配置。

---

### 1.2 服务端验证验证码 — 验证码复用 Bug

**场景**：服务端生成验证码后，在页面不刷新的情况下，该验证码在约 5 分钟内持续有效。

**本质**：验证码变成了一个有时效的"校验令牌"，而非一次性校验凭证。

**利用方式**：在验证码有效期内，使用 Burp Suite Repeater 反复发送携带同一验证码的登录请求，搭配密码字典进行手工或半自动穷举。

> 这属于服务端验证码实现缺陷：没有在验证成功后立即使验证码失效。

---

### 1.3 客户端校验验证码 — 三种绕过方法

客户端（JavaScript）校验验证码，意味着校验逻辑在浏览器端执行，服务端不校验或信任前端的校验结果。

**方法一：禁用浏览器 JavaScript**

- 在浏览器开发者工具或设置中直接禁用 JS
- 前端校验脚本不再执行，验证码形同虚设

**方法二：替换前端校验脚本**

- 在开发者工具中找到负责验证码校验的 JS 脚本
- 使用浏览器本地覆盖（Local Overrides）功能，创建一个修改后的 JS 文件替换原脚本
- 例如：将校验函数改为始终返回 `true`

**方法三："借刀杀人" — 拦截合法请求复用**

- 先手动输入一次正确的验证码
- 使用 Burp Suite 拦截此次登录请求（该请求已通过前端校验）
- 将拦截到的请求发送到 Repeater / Intruder，修改密码字段进行穷举
- 服务端收到的是"已通过前端校验"的合法格式请求，不会再次触发前端校验

> **纠正与补充**：方法三可行不是因为"Burp 抓到的包通过了前端校验所以 Repeater 无需再校验"——实际上，这是因为**服务端本身就没有做验证码校验**（或校验逻辑有缺陷）。如果服务端正确地独立校验验证码，那么即使请求绕过了前端，服务端仍会拒绝。本质上，这是一种**服务端信任前端校验结果**的漏洞，而非 Burp Suite 的特性。

---

### 1.4 Token 防爆破 — CSRF Token 模式

**场景**：每次 HTTP 响应中包含一个隐藏的 `<input type="hidden">` 标签，其 `value` 为一次性 token。下一个登录请求必须携带该 token，token 使用一次后失效。

**配置要点（Burp Suite Intruder）**：

1. **Attack type**：选择 **Pitchfork attack**（叉子攻击）
   - 适用于多个 payload 需要**同步配对**的场景
   - 请求 N 携带的 token 来自响应 N-1

2. **Payload 设置**：
   - Payload 1（密码）：载入密码字典
   - Payload 2（token）：
     - 在 Intruder → Options → **Grep - Extract** 中添加规则
     - 用正则表达式匹配响应中的 token 值
     - Payload type 选择 **Recursive grep**
     - 初始请求中需手动填入第一个有效 token（或先发一个请求获取）

3. **线程池设为 1**：
   - 防止并发请求导致 token 与请求错配（条件竞争）
   - 线程为 1 时，请求严格串行：请求1 → 响应1（含新token） → 请求2（使用响应1的token） → ...

> 用户将条件竞争的风险描述为"同一时间一个 token 匹配多个 HTTP 请求或一个 HTTP 请求匹配多个 token"，这个理解方向正确。更精确地说：如果并发 > 1，请求 2 可能在请求 1 的响应返回之前就发出了，导致请求 2 仍使用旧 token 而非新 token，造成 token 重复使用而失败。

---

### 1.5 IP 请求频率限制 — X-Forwarded-For 伪造

**场景**：同一 IP 最多请求 5 次，超过则拒绝。

**解决方案**：通过 `X-Forwarded-For` 请求头伪造来源 IP。

**配置要点**：

- `X-Forwarded-For: 192.168.2.${i}`
- `${i}` 为 Intruder 的一个 payload 变量
- **Pitchfork attack** 模式，密码与 IP 变量同步配对
- 密码字典约 500 条，可用 IP 范围（192.168.2.2 ~ 192.168.2.254）共 252 个整数 IP

**关键技术 — 小数步长拉伸 IP 范围**：

| 参数 | 取值 | 说明 |
|------|------|------|
| 步长 | 0.2 | 每 5 个递增 `i` 值对应同一个整数 IP |
| 整数处理 | 向下取整（小数点最大设为 0） | 192.168.2.2.2 → 192.168.2.2 |
| 效果 | 每个整数 IP 可发起 5 次请求 | 252 × 5 = 1260 次，覆盖 500 条密码绰绰有余 |

> **这是一个很好的思路**：当可用 IP 数不足以一对一匹配密码时，通过小数步长让每个整数 IP 复用多次，充分利用了"每个 IP 5 次"的配额限制。这种"资源复用"思维在渗透测试中非常实用。

---

### 1.6 IP 限制 + Token 限制 — 组合防护

**场景**：同时存在 IP 请求频率限制和 Token 防爆破。

**配置**：三个 payload 变量，Pitchfork attack，线程池 = 1。

| Payload | 内容 | 来源 |
|---------|------|------|
| Payload 1 | `X-Forwarded-For: 192.168.2.${i}` | 数值递增（小数步长） |
| Payload 2 | 密码（或用户名） | 字典文件 |
| Payload 3 | CSRF Token | Grep - Extract + Recursive grep |

> 方法本质是前两种技术的叠加，配置更繁琐但原理不变。

## 二、压缩包密码穷举攻击

### 2.1 通用流程

```
压缩包 → JtR 提取 hash → hashcat.net 识别算法编号 → Hashcat 碰撞
```

### 2.2 详细步骤

**Step 1：提取 Hash**

```bash
# ZIP 压缩包
zip2john target.zip > hash.txt

# RAR 压缩包
rar2john target.rar > hash.txt
```

**注意**：`zip2john` / `rar2john` 有时会提取出多个 hash 值：
- **第一个 hash** 通常是压缩包最外层的加密 hash（即打开压缩包需要的那层密码）
- 后续的 hash 可能是压缩包内部嵌套的加密文件 hash
- 破解压缩包密码时，选择**第一个 hash** 即可

> **纠正与补充**：用户描述"第一个为最外层压缩包 hash 值，后面为压缩包内部的 hash"基本正确，但更准确地说：多 hash 出现是因为压缩包内包含多个加密条目（如多个加密文件），每条对应一个 hash。对于 ZIP，每个加密文件有独立的加密头；对于 RAR，通常只有一个 hash（文件头加密）。如果压缩包内只有一个加密文件，通常只输出一个 hash。**如果有多个 hash，选择 `$zip2$` 或 `$rar5$` 开头的第一个即可。**

**Step 2：识别 Hash 算法**

- 取 hash 值的**前几个特征字符**（如 `$zip2$`、`$rar5$`、`$pkzip2$` 等）
- 访问 [hashcat example_hashes](https://hashcat.net/wiki/doku.php?id=example_hashes) 进行比对
- 找到对应的 hash 模式编号（即 `-m` 参数值）

**Step 3：Hashcat 碰撞**

```bash
hashcat -m <模式编号> hash.txt /path/to/wordlist.txt
```

常用参数：

| 参数 | 说明 |
|------|------|
| `-m` | 指定 hash 算法编号 |
| `-a 0` | 字典攻击模式（默认） |
| `-a 3` | 掩码攻击（暴力穷举） |
| `-O` | 优化模式，加速但限制密码长度 |
| `--force` | 强制运行（某些环境下需要） |
| `-o` | 将破解结果输出到文件 |

## 三、总结与补充

### 你的理解中正确的地方

1. **穷举攻击的本质概括准确**：无论是 Web 登录还是压缩包破解，核心都是通过大量尝试来碰撞出正确结果。
2. **Token 防爆破的 Pitchfork attack 模式理解正确**：同步配对是此类场景的关键。
3. **线程池设为 1 的理由正确**：避免并发导致的 token 竞争/错配。
4. **X-Forwarded-For 小数步长技巧**：充分利用每个 IP 的配额限制，体现了资源最大化利用的思维，这是很实用的技巧。
5. **压缩包破解流程完整**：JtR 提取 → hashcat 识别 → Hashcat 爆破，流程正确。

### 需要注意/纠正的地方

1. **"Recursive grep" 不是正则表达式本身**：在 Burp Suite 中，Recursive grep 是一种 **payload type**（payload 类型），它的数据来源是 Grep - Extract 从上一个响应中提取的值。正则表达式是在 Grep - Extract 规则中配置的，用于定位和抓取 token，两者是不同层面的配置。

2. **客户端验证码绕过的方法三**：前面已经分析过，根本原因是服务端本身未做验证码校验，而非 Burp Suite "绕过了"前端校验。

3. **条件竞争（Race Condition）的精确描述**：线程池 > 1 时导致 token 失效的原因是请求顺序与响应顺序不匹配，而非 token 与请求的"多对多"映射——串行处理保证了请求 N+1 一定在请求 N 的响应到达后才发送。

4. **Hash 识别方法**：取"前几个字符"去 hashcat example_hashes 页面对比是实用方法，但要注意：某些 hash 格式的特征不止在前几个字符，完整比对更可靠。推荐直接搜索完整的 hash 前缀（如完整的 `$zip2$*1*2*0*...` 开头部分）。

5. **ZIP 加密类型**：ZIP 有两种加密方式——传统 ZipCrypto（弱，可用 `zip2john` 提取）和 AES-256（强，hashcat 模式不同）。`zip2john` 输出的 hash 格式可以区分二者，hashcat 对应的 `-m` 参数也不同。

### 关键工具速查

| 工具 | 用途 | 备注 |
|------|------|------|
| Burp Suite Intruder | Web 表单穷举 | Sniper / Battering ram / Pitchfork / Cluster bomb 四种模式 |
| Burp Suite Repeater | 单请求重放 | 配合有效 token/验证码使用 |
| Hydra | 网络服务登录穷举 | CLI 工具，支持多种协议（SSH、FTP、HTTP 等） |
| zip2john / rar2john | 提取压缩包密码 hash | 来自 John the Ripper (jumbo) |
| Hashcat | GPU 加速 hash 碰撞 | 支持字典攻击、掩码攻击、规则攻击等 |
| [hashcat example_hashes](https://hashcat.net/wiki/doku.php?id=example_hashes) | Hash 算法识别参考 | 页面列出数百种 hash 格式及其对应 `-m` 编号 |

## 附录：Burp Suite Intruder 四种 Attack Type

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| **Sniper** | 单个 payload，逐个变量位置试探 | 单变量穷举 |
| **Battering ram** | 单个 payload，所有变量位置填入相同值 | 多位置但同值的场景 |
| **Pitchfork** | 多个 payload，同步配对（1-to-1） | Token + 密码同步（今天的场景） |
| **Cluster bomb** | 多个 payload，笛卡尔积（全部组合） | 用户名 + 密码全组合穷举 |
