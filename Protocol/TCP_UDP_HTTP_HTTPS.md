# TCP、UDP、HTTP、HTTPS 之间的关系

## 一、OSI 层次定位

```
+--------------------+---------------------------+
| 应用层             | HTTP / HTTPS / DNS / ...  |
+--------------------+---------------------------+
| 表示层             | TLS（HTTPS 的加密层）       |
+--------------------+---------------------------+
| 会话层             |                           |
+--------------------+---------------------------+
| 传输层             | TCP / UDP                 |
+--------------------+---------------------------+
| 网络层             | IP                        |
+--------------------+---------------------------+
| 数据链路层 / 物理层 | 以太网 / Wi-Fi / ...       |
+--------------------+---------------------------+
```

核心关系：

- **TCP 和 UDP** 同属传输层，是并列的两种传输协议，解决"数据怎么送过去"的问题。
- **HTTP** 位于应用层，解决"数据表示什么语义"的问题，依赖下层传输协议。
- **HTTPS** = HTTP + TLS，TLS 在 HTTP 和传输层之间插入加密层。

## 二、TCP 与 UDP：传输层的两种选择

### 2.1 协议定位

| 维度 | TCP | UDP |
|------|-----|-----|
| 中文名 | 传输控制协议 | 用户数据报协议 |
| 连接模型 | 面向连接（先建立连接，再传数据） | 无连接（直接发送） |
| 可靠性 | 可靠：确认重传、排序、去重 | 不可靠：发出去就完了 |
| 顺序 | 保证有序到达 | 不保证顺序 |
| 数据边界 | 流式（无消息边界，字节流） | 数据报（保留消息边界） |
| 流量控制 | 滑动窗口 | 无 |
| 拥塞控制 | 有（慢启动、拥塞避免、快速恢复） | 无（应用层自行控制） |
| 头部开销 | 20 字节（不含选项） | 8 字节 |
| 适用场景 | 文件传输、网页、邮件、SSH | 视频直播、DNS、VoIP、游戏 |

### 2.2 TCP 为什么可靠

TCP 通过以下机制在不可靠的 IP 层之上建立可靠连接：

**三次握手（建立连接）：**

```
客户端                             服务器
  |                                  |
  |—— SYN, seq=x ───────────────────→|
  |                                  |
  |←─ SYN+ACK, seq=y, ack=x+1 ──────|
  |                                  |
  |—— ACK, seq=x+1, ack=y+1 ───────→|
  |                                  |
  |==== 连接建立，开始传数据 ===========|
```

**四次挥手（断开连接）：**

```
客户端                             服务器
  |                                  |
  |—— FIN, seq=u ───────────────────→|
  |                                  |
  |←─ ACK, seq=v, ack=u+1 ──────────|
  |                                  |
  |←─ FIN, seq=w, ack=u+1 ──────────|
  |                                  |
  |—— ACK, seq=u+1, ack=w+1 ───────→|
  |                                  |
  |== TIME_WAIT 2MSL 后关闭 ==========|
```

**数据传输中的可靠机制：**
- **确认与重传**：每个字节有编号，接收方回复 ACK，发送方超时未收到 ACK 则重传
- **校验和**：检测数据在传输中是否损坏
- **去重**：接收方丢弃重复的报文段
- **排序**：接收方按序号重新排列乱序到达的报文段
- **窗口控制**：接收方告知可接收窗口大小，发送方据此调节速率

### 2.3 UDP 为什么快

UDP 不做连接建立，不做确认重传，不做拥塞控制，发出去就是发出去。代价是丢包、乱序、重复全交给应用层处理。

**UDP 伪头部（用于校验和计算，不实际传输）：**

```
+--------+--------+
| 源 IP 地址      |  4 字节
+--------+--------+
| 目的 IP 地址    |  4 字节
+--------+--------+
| 保留  | 协议号  |  2 字节（协议号 17 = UDP）
+--------+--------+
| UDP 长度        |  2 字节
+--------+--------+
```

这个伪头部的存在说明：UDP 虽然简单，但校验和覆盖了 IP 层的地址信息，能检测出 IP 地址被篡改的情况。

### 2.4 TCP 的局限：队头阻塞（Head-of-Line Blocking）

TCP 保证有序交付。如果序列中某个包丢了，后续所有包即便已经到达也要在缓冲区等待，直到丢失的包重传成功。这在 HTTP/2 的多路复用场景下成为瓶颈：一个 TCP 连接上多路复用的所有流共享同一个丢包重传队列，一个流的丢包阻塞所有流。

## 三、HTTP 与 TCP 的关系

### 3.1 HTTP/1.1 over TCP

```
应用层     HTTP（请求-响应文本协议）
              ↓ 序列化为字节流
传输层     TCP（可靠字节流，处理分片/重传/排序）
              ↓
网络层     IP
```

HTTP/1.1 依赖 TCP 提供的可靠字节流：
- TCP 处理丢包重传，HTTP 不需要操心数据完整性
- TCP 处理流控和拥塞控制，HTTP 不需要操心发送速率
- HTTP 只管把请求/响应按格式序列化为字节流交给 TCP

**HTTP/1.1 的连接模型：**

- **短连接**：每次请求/响应结束后关闭 TCP 连接（HTTP/1.0 默认）
- **持久连接**（Keep-Alive）：一个 TCP 连接上串行发送多个请求（HTTP/1.1 默认）
- **管线化**（Pipelining）：不等响应就连续发送多个请求（理论上可并行，实际因队头阻塞几乎废弃）

每个 TCP 连接从建立到关闭经历：
```
DNS 解析 → TCP 三次握手（1 RTT）→ TLS 握手（HTTPS，1-2 RTT）→ HTTP 请求/响应 → TCP 四次挥手
```

### 3.2 HTTP/2 over TCP

HTTP/2 在单个 TCP 连接上实现了真正的多路复用：

```
HTTP/2 流 1  ─┐
HTTP/2 流 2  ─┤ → 帧（Frame）交织在一个 TCP 连接上 → 解复用 → 各流独立处理
HTTP/2 流 3  ─┘
```

优点：多个请求/响应共享一个 TCP 连接，避免 HTTP/1.1 的 6-8 连接限制和连接建立开销。

缺点：TCP 层的队头阻塞仍然存在。所有流共享同一个 TCP 丢包重传队列，一个丢包拖慢所有流。HTTP/2 的流是逻辑上的，改变不了 TCP 层的顺序交付语义。

### 3.3 HTTP/3：从 TCP 转向 UDP

HTTP/3 不再基于 TCP，而是基于 QUIC（Quick UDP Internet Connections），QUIC 又基于 UDP：

```
应用层     HTTP/3（语义同 HTTP/2）
              ↓
"传输层"   QUIC（在 UDP 之上实现了类 TCP 的可靠传输 + TLS 1.3 加密）
              ↓
传输层     UDP（仅作为"载体"，利用 UDP 可以穿透 NAT/防火墙的特性）
              ↓
网络层     IP
```

**为什么换 UDP：**

| 问题 | TCP 的情况 | QUIC/UDP 的解决 |
|------|-----------|----------------|
| TCP 队头阻塞 | 丢一个包阻塞整个连接所有流 | QUIC 的流之间独立，一个流丢包不影响其他流 |
| 连接建立延迟 | TCP 握手 + TLS 握手 = 2-3 RTT | QUIC 内置 TLS 1.3，1-RTT（甚至 0-RTT 恢复） |
| 连接迁移 | 连接由四元组（src_ip, src_port, dst_ip, dst_port）标识，IP 变了就得重连 | QUIC 使用 Connection ID 标识连接，Wi-Fi 切 4G 无感切换 |
| 协议僵化 | 中间设备（防火墙/NAT）深度解析 TCP 头，新扩展难以部署 | QUIC 头部大部分加密，中间设备只能看到极少字段，易于演进 |
| 握手加密 | TCP 握手完全明文 | QUIC 握手自带 TLS 1.3，握手过程本身加密 |

**QUIC 做了什么：**

QUIC 在 UDP 之上重新实现了一套可靠传输机制：
- 连接管理（Connection ID + 版本协商）
- 可靠传输（确认 + 重传，但流级别独立）
- 流复用（每个流独立的有序字节流，互不阻塞）
- 拥塞控制（类似 TCP NewReno/CUBIC，但在用户空间实现，可随应用更新而更新）
- 内置 TLS 1.3（加密是强制开启的，没有明文模式）

## 四、HTTPS 与 TCP 的关系

### 4.1 协议栈

```
应用层     HTTP
              ↓
安全层     TLS（加密 + 认证 + 完整性）
              ↓
传输层     TCP（可靠字节流）
              ↓
网络层     IP
```

HTTPS 在 HTTP 和 TCP 之间插入 TLS 层。TLS 依赖 TCP 的可靠字节流来保证握手消息的完整性——TLS 记录协议的 MAC（消息认证码）计算基于顺序到达的假设，如果 TCP 丢包乱序，TLS 连接会直接断开而非尝试恢复。

### 4.2 TLS 对 TCP 的影响

**增加的 RTT：**

```
纯 HTTP：  TCP 握手（1 RTT）                     = 1 RTT
HTTPS：    TCP 握手（1 RTT）+ TLS 1.2 握手（2 RTT）= 3 RTT（最坏）
           TCP 握手（1 RTT）+ TLS 1.3 握手（1 RTT）= 2 RTT
           TCP 握手（1 RTT）+ TLS 1.3 0-RTT        = 1 RTT（恢复连接）
HTTP/3：   QUIC 握手（内置 TLS 1.3，1 RTT）         = 1 RTT（首次）
           QUIC 0-RTT                              = 0 RTT（恢复连接）
```

**TLS Record 分片：**

TLS 将应用数据切成 TLS Record（最大 16KB），加密后交给 TCP。TCP 可能再对 TLS Record 进行分段（MSS 约 1460 字节）。这意味着一个 HTTP 响应可能经过两层分片：

```
HTTP 响应体（N KB）
  → TLS 切成多个 16KB Record
    → TCP 切成多个 MSS 大小的段
      → IP 分片（若超过 MTU）
```

## 五、HTTPS 与 UDP 的关系（HTTP/3）

在 HTTP/3 中，HTTPS 不再经过 TCP，而是 QUIC + UDP：

```
应用层     HTTP/3
              ↓  语义同 HTTP，但传输编码用 QPACK（替代 HPACK）
"传输+安全" QUIC
    ├─ 可靠传输（流级别，替代 TCP）
    ├─ TLS 1.3 加密（替代独立的 TLS 层）
    └─ 多路复用（流复用，替代 HTTP/2 的帧复用）
              ↓
传输层     UDP（仅提供端口号和校验和，QUIC 把自己装到 UDP 载荷里）
              ↓
网络层     IP
```

QUIC 把传输可靠性和加密做在了一起，不再分层。TLS 1.3 的握手直接运行在 QUIC 帧上，不需要 TCP 先建立连接。

**实际效果：**

- TCP 经过多年优化，操作系统内核中有成熟的实现（TSO/GRO 等硬件卸载）
- QUIC 在用户空间实现，更灵活但 CPU 开销更高（正在通过内核 QUIC 和硬件加速改善）
- 经过中间设备（NAT/防火墙）时，UDP 可能被限制（限速/封禁），部分网络对 UDP 不够友好
- Google 和 Cloudflare 的数据显示 HTTP/3 在实际网络中延迟降低 15-30%

## 六、关系总结

### 6.1 依赖关系图

```
                       HTTP（应用层语义）
                      /    |          \
                     /     |           \
              HTTP/1.1   HTTP/2       HTTP/3
              over TCP   over TCP     over QUIC
                |           |            |
               TLS        TLS         QUIC（内置 TLS）
                |           |            |
               TCP        TCP           UDP
                 \         /            /
                  \       /            /
                   \     /            /
                        IP
```

### 6.2 核心结论

| 关系 | 说明 |
|------|------|
| TCP vs UDP | 同属传输层，互补关系。TCP 保证可靠有序，UDP 保证低延迟无连接。选择取决于场景需求。 |
| HTTP vs TCP | 上下层依赖关系。HTTP/1.1 和 HTTP/2 必须依赖 TCP（或类 TCP 的可靠传输）。HTTP 不关心 TCP 的重传/流控细节。 |
| HTTP vs HTTPS | HTTP + TLS = HTTPS。协议语义完全相同，只是传输通道加了加密层。HTTP/3 中加密是内置的，不存在明文版本。 |
| HTTPS vs TCP | HTTPS 依赖 TCP 的可靠性来保证 TLS 握手的完整性。但 TCP 的队头阻塞也拖累了 HTTP/2 的性能。 |
| HTTPS vs UDP | HTTP/3 把加密传输搬到了 UDP 之上，摆脱了 TCP 队头阻塞，但付出了用户空间实现的 CPU 代价。 |
| HTTP/3 vs HTTP/2 | HTTP/3 不改变 HTTP 语义（方法/头部/状态码不变），只改变底层传输。对应用开发者透明。 |

### 6.3 一句话类比

**TCP 是邮局的挂号信**——签字确认、按序送达、丢件补发；**UDP 是往信箱里塞传单**——塞进去就不管了，丢了也不知道。

**HTTP 是信的内容格式**——抬头、正文、签名有固定写法；**HTTPS 是把信装进密码信封**——邮递员能看到信封上的地址，但看不到里面写了什么。
